### 5.1 workbuddy 4.6.7 的严重 bug（升级的真实理由）

**CHANGELOG 4.7.0 记录**：DSH 0.2.1-rc.1 起随包 `pi-ai` 1.1.0，而 pi-ai 1.1.0 **只读 `messages`**（走 `resolveTranscript` / `collapseSystemMessages`），**从不读顶层 `systemPrompt` / `tools`**。

workbuddy 4.6.7 的 `withLegacyContext(api, generation)` 在 modern 分支是：

```js
if (generation === "modern") return api;
```

→ 原样透传 0.85 形状的信封 → **system prompt 与工具声明全部静默丢失**。

**实测确认**：`import.meta.resolve('@earendil-works/pi-ai')` 从 workbuddy 目录解析到
`source/node_modules/.pnpm/@earendil-works+pi-ai@1.1.0.../dist/index.js`
→ 判定 `generation="modern"` → 命中 bug。

**4.7.0 用 `foldModernContext()` 修好**（把顶层 systemPrompt/tools 折进首条 system 消息）。

另 4.8.0 修：跨区切换后会话卡死 `400 code 11115 prompt is too long`（用宿主自己的 `compactRegion` 分块折叠，块上限 = 窗口 35%，目标 60%）。4.8.1 只改 UI 样式。

**结论：升级是必须的，不是可选的。**

## 6. 三个"看似有问题、实际不是"的结论

### 6.1 tool-gate 是空转的 → 本版已整个禁用

**上一版说它"空转"是对的**。审计日志 `%TEMP%\dsh-tool-gate.log`（250KB）显示：`preset=cordis` 会拦 `dev_*`，白名单 `["cordis","prompt-writing"]`；但 **18 个 `dev_*` 工具随 super-injector（10-11 卸载）已不存在** → 无待挡工具。

**处置**：整个 bundle 移除（13 → 12 层）。审计日志确认无实际拦截后执行。

### 6.2 auto-review「从不触发」→ 上一版结论是**错的**

**上一版 §6.3 说 auto-review 从不触发，这是错的。**

实际源码 `source/packages/experimental/auto-review/src/index.ts:689`：只在 `presets !== auto` 时跳过，**非 auto 走"规则先行 + 失败再问 LLM"路径**，是活的。

**但当前确实空转**：因为 `permission.defaultPreset: danger-full-access` 且 `approval: never`，**没有审批弹窗可审**。所以"空转"的结论对，但**原因是权限配置，不是插件坏了**。

**建议**：保留。若改成 `approval: on-request` 会自动生效。

### 6.3 429 `model_busy` 不重试 → 有意设计，不该改

- `source/packages/llm/llm/src/retry-policy.ts:14-20`：`DEFAULT_RETRYABLE_CODES = [EMPTY_RESPONSE, RATE_LIMIT, SERVER, TIMEOUT, TRANSPORT]`，**QUOTA 不在其中**
- workbuddy 插件刻意把 `model_busy` 译成 `quota_exceeded`（`lib/index.js:1863` `KIND_HOST_CODE`），长注释论证：

  > "A model that is loaded for everyone will not clear inside one turn's backoff, so spending five attempts on it delays the honest answer without ever producing one."

- **UI 不会静默**：`packages/client/ui-chat/src/client/apply.ts:105-111` 监听 `turn/end`，`code` 为 `QUOTA`/`ACCOUNT_QUOTA` 时 `quotaNotice.set(...)` → 帧级横幅

**结论：不改代码。** 若把 QUOTA 加进全局重试名单，会让**真正的余额耗尽反复重试**（`error.ts:28`、`llm-deepseek/src/transport.ts:30` 的 `status === 402` 也归 QUOTA）。

**症状**：会话在 CN 区用 `reasoningEffort: "max"`，切到国际区（`workbuddy-global`）后该字段**消失**，退回 provider 默认 `"high"`。

**取证**（当前会话日志解压后）：
```
request/header seq=12   {"provider":"workbuddy","model":"deepseek-v4.1-flash","reasoningEffort":"max"}
request/header seq=291  {"provider":"workbuddy","model":"deepseek-v4.1-flash","reasoningEffort":"max"}
model/selection seq=767 {"provider":"workbuddy-global","model":"deepseek-v4.1-flash"}      ← 无 effort
request/header seq=774  {"provider":"workbuddy-global","model":"deepseek-v4.1-flash"}      ← 无 effort
request/header seq=835  {"provider":"workbuddy-global","model":"deepseek-v4.1-flash"}      ← 无 effort
```

**根因**：`source/packages/acp/acp/src/model-control.ts` 的 `set()` 中 `MODEL_CONFIG_ID` 分支只调 `resolveSelection(selected)`，**不携带旧 effort**；只有 `REASONING_CONFIG_ID` 分支才写入。随后 `packages/llm/llm/src/index.ts:915-935` `resolveCallWithInfo` 在 `requested === undefined` 时用 `reasoning.defaultEffort`；workbuddy 两区 defaultEffort 都是 `"high"`。

**修复**（`model-control.ts`）：
```ts
const carried = await this.carryReasoningEffort(current.reasoningEffort, selected, signal)
const next: ModelSelection = {
  provider: selected.provider,
  model: selected.model,
  ...carried === undefined ? {} : { reasoningEffort: carried },
}
await this.resolveSelection(next, signal)
this.selected = next
```

新增私有方法：
```ts
private async carryReasoningEffort(
  effort: ModelSelection['reasoningEffort'],
  target: ModelSelection,
  signal?: AbortSignal,
): Promise<ModelSelection['reasoningEffort']> {
  if (effort === undefined) return undefined
  const info = await this.llm.resolveModelInfo(target.provider, target.model, signal)
  return info.reasoning?.efforts.some(candidate => candidate.id === effort) === true ? effort : undefined
}
```

**理由**：目标模型支持该 effort 就带走；不支持则丢弃，让目标自己的 default 生效（这与 reasoning 选项的显示一致，不会撒谎）。

**测试**：`source/packages/acp/acp/tests/model-control.spec.ts` 追加 2 个回归用例
- `carries the live reasoning effort across a model switch`
- `drops a reasoning effort the target model does not advertise`

**结果**：`7 tests passed (7)`；`npx tsc -p tsconfig.json --noEmit` 零输出（通过）。

### 7.2 【已否决】给 workbuddy 加 `thinkingTokenBudgetField`

**假设**：workbuddy 的 `toPiModel()` 只设了 `compat:{supportsReasoningEffort:true}`，没设 `thinkingTokenBudgetField` → 本地算的 16384 thinking 预算发不出去 → 思考失控。

### 7.3 【已查明】"截断"的三重成因

用户描述："思考很久然后只吐出一小段就停了" + "输出到一半突然停住，没有任何报错，发 Continue 能接着写"。

**硬数据**：当前会话 seq ≥ 900 的 79 条 assistant 消息
- reasoning 合计 **116,100 字符**
- 可见 text 合计 **2,652 字符**
- 比值 **97.8% : 2.2%**
- 典型：`seq=1050` reasoning 10,736 字符 → text **0**；`seq=1092` 10,596 → 52；`seq=1222` 9,887 → 37

**成因一：思考占比压倒性**（主因，观感为"吐一小段就停"）
173 条 assistant 消息的 `stopReason` **全部是 `toolUse`**，**没有一条是 `length`** → 不是 max_tokens 撞顶，而是思考极长、可见输出极短。

**成因二：429 `model_busy` 直接失败**（真正的"无报错停住"）

**成因三：`UNKNOWN_MODEL` 瞬时错误**

**已排除的假设**：
- ❌ 不是 max_tokens 太小：两区 `maxTokens=128000`、`contextWindow=1000000`；`clampMaxTokensToContext`（`pi-ai/dist/api/simple-options.js:20-27`）在上下文 < 868K 时恒为 128000，本会话实际 totalTokens 才 ~100,784

### 11.2 决定性差异：预设内 compaction-basic 的处理

这是换包的核心原因，也是移植版**结构性做不到**的事。

**实测事实**（`--dump-config` 核实）：宿主层 `compaction-basic` 两版都禁用了，但 **15 个预设各自在 `isolate:{compaction:true}` 里挂的那份 `compaction-basic` 一直活着**。

- 移植版 `cordis.patch.yml` 原文：「Shipped presets keep their realm-local compaction-basic fallback」→ **有意保留**
- 上游做法：`bili-native` 条目注册 cordis `internal/config` 挂钩，递归把预设内 `@deepseek-ai/dsh-compaction-basic` / `command-compact` 行改成 `disabled: true`（#3354）

上游实现（从 `dsh-native.js` 提取）：
```js
function disableBasicCompaction(rows) {
  return rows.map(row => {
    if (row === null || typeof row !== 'object') return row;
    const r = row;
    if (r.name === DSH_COMPACTION_BASIC_PACKAGE || r.name === DSH_COMMAND_COMPACT_PACKAGE) {
      return { ...r, disabled: true };
    }
    if (r.group && Array.isArray(r.config)) return { ...r, config: disableBasicCompaction(r.config) };
    return row;
  });
}
ctx.on('internal/config', function (_raw, next) {
  const resolved = next();
  if (this?.entry?.options?.name !== DSH_AGENT_PRESET_PACKAGE) return resolved;
  const config = resolved ?? {};
  if (!Array.isArray(config.plugins)) return resolved;
  return { ...config, plugins: disableBasicCompaction(config.plugins) };
}, { global: true });
```

**为什么 profile 层 patch 做不到**（源码实证）：
`source/node_modules/.pnpm/.../cordis-plugin-include/src/index.ts` 的 `applyEntryPatches`：
```ts
for (const [key, value] of Object.entries(overrides)) {
  if (key === 'id') continue
  target[key] = value        // ← 浅覆盖，config 整体替换
}
```
且索引只建给 `entry.group && Array.isArray(entry.config)` 的条目。预设行的 `config` 是**对象**（`{id, order, plugins}`）且无 `group` 标记 → **预设内的嵌套行永远无法按 id 定位**。硬写 `- id: preset-ptc` + `config` 会整体替换掉 `id`/`order`，roster 直接识别不了该预设。
