# 设计连续性管理（game-continuity）

## 何时使用
- 每轮对话开始检阅项目时（快速核查本阶段涉及文档与既有确认的咬合）。
- 每阶段产出落盘前（全量核查一次）。
- 修改已确认设计后（检查对下游文档的影响面）。
- 用户指出「前后矛盾」「设定冲突」「数值对不上」时（定位并请用户裁决）。

## 检查清单
1. 创意 ↔ 系统：核心循环与玩法系统是否兑现了 00-创意/brainstorm.md 的目标体验与核心卖点；出现偏离时是升级创意还是调整系统，请用户裁决。
2. 系统 ↔ 系统：各系统的输入输出接口对得上（A 需要的数据确有系统产出），同类情形下的规则不冲突，存在优先级规则。
3. 数值 ↔ 系统：每个数值都挂在某个系统规则上（引用系统与规则编号）；公式的变量、单位、取整与边界齐全，他人代入可复算。
4. 经济 ↔ 进度：产出与消耗净流与成长阶段匹配；奖励强度相对同期进度合理；无「只产出不回收」的资源。
5. 进度 ↔ 内容：每个解锁点都有承担引导责任的内容条目；难度曲线与能力曲线同步，跳跃点有说明。
6. 世界观 ↔ 系统与内容：特殊规则的机制、代价与边界在所有场合一致；叙事角色的动机与玩法职能不相互违背。
7. 单位 ↔ 数值与关卡：units.md 的能力与行为和关卡投放规格一致，数值区间引用 01-系统/economy.md 编号而非另立一套。
8. 大纲 ↔ 设定：事件序列符合世界观规则与角色动机；大纲只含设计与结构层级内容（无台词、无脚本实现）。
9. 结构表 ↔ 大纲正文：03-大纲/structure.md 的条目编号、节奏定位与前置依赖和正文逐条对应。
10. 资产 ↔ 前四阶段：每项资产条目都能追溯到一个玩法或内容需求；清单不自行引入新设定。
11. 时间线与名词：新事件与专有名词以 timeline.md 与 glossary.md 为基准登记。

## 方法
- 用检索工具全局搜索关键名/术语（系统名、规则编号、数值编号、内容条目编号、单位名、地名、组织名），对比出现处的上下文。
- 以已确认文档（README 的确认记录 + 各阶段文档）为基准；草稿中的新事实须经用户确认后，才反向补录进基准。
- 跨阶段长线内容（伏笔、事件链、规则后果、待补设计）在 continuity-log.md 中单独列「追踪事项」小节登记。
- 数值一致性优先用复算验证：抽取关键节点代入公式试算，结果与文档记录不符即列为冲突。

## 冲突处理
1. 发现新产出与已确认内容冲突时，先指出冲突并说明两种口径各自的来源，请用户裁决，不得自行选择其一后直接改写正式设定。
2. 裁决完成后必须记录：日期、冲突内容、裁决结果、修改了哪些文件。
3. 修改影响面大于单文件时（如改系统编号、改数值口径、改内容条目编号），先全局检索全部出现位置，列出改动清单，经用户确认后逐处执行，最后全局复查一遍。

## continuity-log.md 格式（04-修订/continuity-log.md）
```markdown
# 设计连续性记录
## <日期>
- 查证：<冲突内容与双方口径来源>
- 裁决：<以谁为准、用户如何裁决>
- 修改：<改动的文件清单>

## 追踪事项
- <待补设计/伏笔/规则后果/待确认数值，标注所在文档与责任阶段>
```
