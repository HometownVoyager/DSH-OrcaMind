# 游戏项目搭建（game-project-bootstrap）

## 何时使用
- 用户提出开始一款新的游戏设计项目、且尚无项目目录时（先与用户确认品类、平台与项目边界，再执行本 skill）。
- 用户要求「新建游戏项目」「开新项目」「把这份创意立成项目」时。
- 每轮对话开始检阅项目状态、每阶段结束时更新进度与确认记录。
- 接手已有项目但缺 README.md 时：先按本 skill 模板补建（已有内容照实填入，不确定处标注待确认），再展开工作。
- 项目实为视觉小说/文字冒险品类时同样用本 skill 建目录，并在 00-创意/ 中记录品类判定与剧本级设计的承接去向（vn-design / screenplay-writing）。

## 执行顺序（本 skill 是每个项目第一步）
1. **开工规范检查**（先于目录搭建或同步进行）：检查工作区主目录的 `规范-游戏设计.md`——
   - 存在用户提供的结构/格式规范且完整 → 直接采用，不再询问；
   - 没有、不全，或与默认规范冲突 → 停下询问，给三个方向由用户选：① 选默认集（本预设内置项目结构与文档体系模板，即下列目录约定与各文档模板）；② 新放一份（用户自备设计文档规范或团队内部规范，可等待放入工作区后继续）；③ 由 agent 当场起草（用 web_search 检索、用 web_fetch 打开原文核对：平台发行规范、引擎项目结构惯例、团队设计文档模板），草稿经用户逐条确认后定稿。
   - 选定后落盘 `规范-游戏设计.md`（统一四节骨架）：①来源记录（规范集名称、出处与定稿日期）②结构与目录约定 ③产出格式规范（文档分层、编号体系、数值表与结构表格式）④红线与禁忌（抽象层级边界、数值口径要求等）。选默认集时汇总引用本 skill 与各阶段 skill 的模板要点，不复制全文。
   - 用户自备规范不全时，在其基础上按所选默认集补全，补全内容标注并经用户确认后并入。
2. **项目登记**：在 README 游戏登记表登记本设计线——名称、类型（品类/类型融合）、目标平台、当前阶段、状态；同一项目多条设计线（主体设计、资料片或续作提案）逐条登记，互不混稿。
3. **基准信息确认**：与用户确认决定后续设计基准的四项——目标平台与操作方式、品类与核心体验目标、制作规模与团队条件、引擎与实现约束；不确定先求证，不凭猜测写进 README。
4. **目录搭建**（结构如下）。
5. **提示下一步**：从 Brainstorm 阶段开始（game-brainstorm → 00-创意/brainstorm.md）。

## 标准目录结构
```
<项目名>/
├── README.md                    # 项目总览：游戏登记表、当前阶段、确认记录（最先创建，每轮先读）
├── 00-创意/
│   └── brainstorm.md            # 阶段1：核心创意/主题立意/情绪基调/目标体验/类型融合/卖点
├── 01-系统/                     # 阶段2（四项深度要求所在）
│   ├── core-loop.md             # 核心循环：玩家反复执行的动作链与反馈
│   ├── systems.md               # 玩法系统及其输入输出与依赖关系
│   ├── economy.md               # 数值与经济：属性公式/成长曲线/产出消耗/货币流转
│   └── progression.md           # 进度与奖励：解锁节奏、奖励结构、反馈强度
├── 02-世界观/
│   ├── world.md                 # 阶段3：世界规则/历史/社会结构
│   ├── factions.md              # 势力与组织
│   ├── geography.md             # 地理与地点（含场景功能与开放关系）
│   ├── timeline.md              # 历史年表（世界史与游戏内事件线）
│   ├── glossary.md              # 专有名词表
│   └── characters/              # 叙事角色档案，每人一个文件
│       ├── relationships.md     # 人际关系网与变化方向
│       └── units.md             # 可交互单位规格：NPC/敌人/可招募角色的系统侧设计
├── 03-大纲/                     # 阶段4
│   ├── content-outline.md       # 内容大纲：章节/关卡/任务级
│   └── structure.md             # 结构表：节奏定位、难度曲线与系统解锁点
├── 04-修订/
│   └── continuity-log.md        # 设计与连续性核查记录、冲突裁决记录（见 game-continuity）
└── 05-资产/                     # 阶段5
    ├── asset-list.md            # 资产总表（规格/数量/优先级）
    └── notes/                   # 分类明细：model / anim / vfx / ui / audio / scene / config / text
```

说明：
- 目录名带数字前缀是为了排序稳定；工作流按 创意（00）→ 系统（01）→ 世界观（02）→ 大纲（03）→ 资产（05）推进，04-修订/ 为跨阶段常驻，非单阶段产出。
- 01-系统/ 四份拆分对应系统设计的四项深度要求（核心循环 / 玩法系统 / 数值与经济 / 进度与奖励），避免数值口径被埋进单一大文件；小体量项目可先只建 core-loop.md 与 systems.md，economy.md 与 progression.md 在进入对应专项时补建（补建须记入 README 进度记录）。
- 全部文件使用 Markdown、UTF-8 编码，标题层级从 `#` 开始。

## README.md 模板
```markdown
# <项目名>

- 项目说明：<一句话，本项目收哪些设计内容>
- 规范集：<规范-游戏设计.md 所选规范集名称>（见工作区 规范-游戏设计.md）
- 当前阶段：<Brainstorm / 核心玩法与系统设计 / 世界观与内容设定 / 内容大纲 / 资产清单>
- 当前进度：<最近完成的阶段产出，如「核心循环 1 版已确认，玩法系统 3/6 项已确认」>
- 下一待确认事项：

## 游戏登记表
| 名称 | 类型/品类 | 目标平台 | 核心循环一句话 | 当前阶段 | 状态 | 备注 |
|------|-----------|----------|----------------|----------|------|------|

## 阶段确认记录
| 日期 | 设计线 | 阶段 | 确认内容 | 用户裁决 |
|------|--------|------|----------|----------|

## 进度记录
| 日期 | 完成内容 | 文件 |
|------|----------|------|
```

## 执行步骤
1. 与用户确认项目名（暂定即可）、品类与平台目标、设计线条数——这些决定后续系统深度与资产规格基准。
2. 执行开工规范检查并落盘 `规范-游戏设计.md`（见上）。
3. 创建目录骨架与 README，README 最先创建并填写已知信息；各阶段文档先不创建或只留占位，按推进逐份补全。
4. 接手已有项目补建 README 时按现有文档照实填写，无法确认的条目标注「待确认」并列入下一待确认事项，不凭空补写。
5. 搭建完成后把项目目录路径与结构告诉用户，并说明下一步（Brainstorm，或用户指定的阶段）。

## 注意事项
- 五阶段顺序为 Brainstorm → 核心玩法与系统设计 → 世界观与内容设定 → 内容大纲 → 资产清单；只有用户确认本阶段完成、或明确指示进入下一阶段后才推进，并在 README 记录该确认。
- 每轮工作以 README.md 为入口：有则先读再干活，无则先建再干活。
- 每阶段产出落盘前按 game-continuity 执行一次全量核查；查出的冲突先请用户裁决，并记入 04-修订/continuity-log.md。
- 用户要求跳转或回溯时照办，但要在 README 与对话中说明跳转对前后阶段可能产生的影响（如系统未定先出资产清单，会因玩法改动而整批返工）。
- 用户已有自己的目录习惯时尊重用户结构，但至少保证创意、系统、世界观、大纲、修订与资产六部分可被找到。
- 规范-游戏设计.md 是唯一规范事实源：修改规范须先经用户拍板并同步更新该文档。
