# 核心玩法与系统设计（game-system-design）

## 何时使用
- 项目处于核心玩法与系统设计阶段（阶段2），或需要修订、细化已确认的核心循环与玩法系统时。
- 用户描述了一段玩法体验（「玩家应该能……」「希望有……的感觉」）需要落成可实现的系统结构时。

## 本阶段边界
本阶段回答「玩家反复做什么、这件事为什么有趣、代价是什么、各系统之间如何咬合」，不细化到关卡编号与任务清单（留给 game-level-design），不写具体数值曲线与公式全表（留给 game-economy），不写界面视觉与美术表现（留给资产阶段）。三者互有引用时写明引用关系，不重复维护同一份内容。

## core-loop.md 模板（01-系统/core-loop.md）
```markdown
# 核心循环

## 一句话循环
玩家在 <场景/情境> 中反复执行 <动作A → 动作B → 动作C>，获得 <反馈/收益>，进而驱动下一轮 <动作A> 的升级或变化。

## 循环分层
- 微观循环（秒级）：<单次操作与其即时反馈>
- 中观循环（分钟级）：<一次战斗/一关/一局的结构>
- 宏观循环（小时级及以上）：<成长、解锁与长线目标>

## 各环节的动作与决策
逐环节写明玩家做什么、面临什么选择、选择的代价与收益；标注哪一环是心流与乐趣的主要来源。

## 反馈与奖励节奏
每个环节的反馈形式（视听/数值/内容解锁）与强度区间；说明反馈延迟与即时性取舍。

## 循环的自我驱动
本轮收益如何转化为下一轮的动机（能力提升/新内容开放/目标推进），以及循环在何时可能失去动力（长线衰减点与对应的破局设计）。

## 开放问题
```

## systems.md 模板（01-系统/systems.md）
```markdown
# 玩法系统

## 系统清单
| 编号 | 系统名 | 职能一句话 | 输入 | 输出 | 依赖系统 | 解锁时机 | 状态 |
|------|--------|------------|------|------|----------|----------|------|

## 各系统设计
### <系统名>
- 玩法描述：玩家在其中做什么、如何操作与决策；
- 内部规则：状态、判定与结果的处理方式（写清规则边界与例外）；
- 与其他系统的接口：接收什么、产出什么、改动谁的数据；
- 提供的体验：该系统承担核心循环的哪一环，服务什么体验目标；
- 代价与取舍：实现复杂度、上手成本、与已确认系统的潜在冲突。

## 系统层体验逻辑
系统机制如何表达主题与体验目标（如有限存档表达代价、可见的成长表达回报）。

## 实现范围与取舍
按目标平台与制作条件划分：必需实现、可选增强、明确不做；每项取舍写明依据。
```

## 执行步骤
1. 以已确认的 00-创意/brainstorm.md 为输入，先写核心循环的分层结构，再逐环节确认玩家的动作与决策。
2. 列全系统清单，逐系统写明内部规则与相互接口；接口对不上的（A 需要的数据 B 不产出）当场标为冲突并请用户裁决。
3. 复核每个系统都能指回核心循环的某一环：指不回的系统列为「候选/待裁决」，不凭复杂度堆系统。
4. 与用户确认实现范围取舍后落盘；数值细化与关卡细化分别提示转入 game-economy 与 game-level-design。

## 注意事项
- 系统必须服务体验：每个机制都要能说清它提供什么体验、玩家因此做出什么不同决策；说不清的机制不进入正式文档。
- 系统实现范围（引擎、平台、制作成本）先与用户确认，再决定机制取舍；不假设团队具备某项实现能力。
- 两个系统的规则在同一情形下给出不同结果时，必须给出优先级规则，不留歧义。
- 本阶段产出的规则条目使用稳定编号（系统编号 + 规则序号），供数值与关卡文档引用。
