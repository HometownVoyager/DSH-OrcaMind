# 公文项目搭建（official-doc-bootstrap）

## 何时使用
- 用户提出新的公文/文书起草需求、且尚未建立项目目录时（先与用户确认文种与受文对象，再执行本 skill）。
- 用户要求「开新项目」「建公文项目」「起草一份函件/通知/报告」时。
- 每轮对话开始检阅项目状态、每阶段结束时更新进度与确认记录。
- 接手已有项目但缺 README.md 时：先按本 skill 模板补建（已有内容照实填入，不确定处标注待确认），再展开工作。

## 执行顺序（本 skill 是每个项目第一步）
1. **开工规范检查**（先于目录搭建或同步进行）：检查工作区主目录的 `规范-公文.md`——
   - 存在用户提供的结构/格式规范且完整 → 直接采用，不再询问；
   - 没有、不全，或与默认规范冲突 → 停下询问，给三个方向由用户选：① 选默认集（党政机关公文 spec-govt-gbt9704 / 企业行政·商务文书 spec-corporate-admin / 法律函件 spec-legal-letters）；② 新放一份（用户自备，可等待放入工作区后继续）；③ 由 agent 当场起草（用 web_search 检索、用 web_fetch 打开原文核对），草稿经用户逐条确认后定稿。
   - 选定后落盘 `规范-公文.md`（统一四节骨架）：①来源记录（规范集名称、出处与定稿日期）②结构与目录约定 ③产出格式规范（标题层级、编号体系、要素格式）④红线与禁忌。选默认集时汇总引用对应 spec skill 的定稿要点，不复制全文。
   - 自备规范不全时，在其基础上按所选默认集补全，补全内容标注并经用户确认后并入。
2. **文书登记**：与用户确认本项目收哪些文书；每份登记文种、受文对象、行文方向与拟用规范集，写入 README 文种登记表。文种判定细节按 doc-types 执行；拿不准先确认，不凭空假设。
3. **目录搭建**（结构如下）。
4. **提示下一步**：每份文书从「文种与受文对象」阶段开始（doc-types），随后进入规范确定（如尚未落盘 规范-公文.md）与依据材料收集。

## 标准目录结构
每个项目一个目录，位于当前工作目录（或用户指定的目录）下，命名为项目名（用户确认的暂定名即可）：

```
<项目名>/
├── README.md                    # 项目总览：文种登记表、当前阶段、确认记录（最先创建，每轮先读）
├── 01-定稿/                     # 定稿归档（版本命名，历史版本只增不改）
├── 02-草稿/                     # 草稿，<文种>-<主题>-v<n>.md
├── 03-依据材料/                 # 政策口径、数据、引用来源、法条原文与证据，逐份注明出处
└── 04-校对记录/                 # 按所选规范逐项校对表（格式/口径/称谓/数字/法律措辞）
```

说明：
- 目录名带数字前缀是为了排序稳定；工作流按 02-草稿 → 校对（04-校对记录）→ 定稿（01-定稿）单向推进，历史版本只增不改。
- 03-依据材料/ 的每份条目注明：文件号/文号、发布机关与日期、统计口径（数据类）、页码或条款定位；法律函件另存法条原文摘录。
- 全部文件使用 Markdown、UTF-8 编码，标题层级从 `#` 开始。

## README.md 模板
```markdown
# <项目名>

- 项目说明：<一句话，本项目收哪些文书>
- 规范集：<规范-公文.md 所选规范集名称>（见工作区 规范-公文.md）
- 当前阶段：<文种与受文对象 / 规范确定 / 依据材料收集 / 解构起草 / 逐项校对 / 审校定稿>
- 当前状态：<一段话说明各文书推进到什么程度>
- 下一待确认事项：

## 文种登记表
| 编号 | 文种 | 受文对象 | 行文方向 | 拟用规范集 | 状态 | 备注 |

> 「行文方向」栏：存在隶属或相隶属关系时填 上行/下行/平行；决议、公报、公告、通告、纪要属会议决议或面向社会的公布，律师函/催告函/告知函/复函属当事人之间，一律填「不适用」并在备注写明依据（判定细则见 doc-types 的行文规则）。
|------|------|----------|----------|------------|------|------|

## 阶段确认记录
| 日期 | 文书 | 阶段 | 确认内容 | 用户裁决 |
|------|------|------|----------|----------|

## 进度记录
| 日期 | 完成内容 | 文件 |
|------|----------|------|
```

## 执行步骤
1. 与用户确认项目名（暂定即可）、文书清单、各文书受文对象与使用场景；不确定先求证，不凭空假设。
2. 执行开工规范检查并落盘 `规范-公文.md`（见上）。
3. 创建目录与骨架文件：README.md 最先创建并填写已知信息；四个子目录创建后可各放一个 `.gitkeep` 或索引文件说明用途。
4. 接手已有项目补建时，README 与登记表按现有内容照实填写，无法确认的条目标注「待确认」并列入下一待确认事项，不凭空补写。
5. 搭建完成后，把项目目录路径与结构告诉用户，并说明下一步（逐份文书从文种与受文对象开始）。

## 注意事项
- 不要在没有项目目录的情况下把草稿或口径写进零散文件——后续校对、依据回溯与进度管理都依赖这个结构。
- 每轮工作以 README.md 为入口：有则先读再干活，无则先建再干活。
- 同一项目多份文书时，每份独立走完六个阶段；不同文书的草稿、依据与校对记录在文件名上区分（文种前缀），不混放。
- 用户已有自己的目录习惯时尊重用户结构，但至少保证 README、四个子目录可被找到。
- 规范-公文.md 是唯一规范事实源：修改规范须先经用户拍板并同步更新该文档。
