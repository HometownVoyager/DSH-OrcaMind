# 提示词常见结构与反模式（prompt-patterns）

## 何时使用
- 结构设计阶段：为一条提示词选定结构并逐层设计要点时。
- 草稿完成后：对现有提示词做结构诊断，检查反模式时。
- 修改阶段：测试未通过项回溯到结构层原因时（配合 prompt-testing 的测试记录）。

## 简单指令型：四段轻量结构
- **角色**：一句身份定义，给出专业域与视角（如「你是一位资深技术文档译者」）；不堆砌形容词，身份要与任务直接相关。
- **任务**：一句动词开头的可执行指令，含交付物（做什么、产出什么）；一次只放一个任务，多个独立任务拆成多条提示词。
- **约束**：3–6 条，覆盖范围、风格、长度、禁忌；每条可核验（能回答「做到了是什么样」）；优先正向表述。
- **输出格式**：字段清单或最小示例二选一；需结构化输出时明确「仅输出 JSON，不要任何多余文字」，并给出字段名与类型。
- 篇幅通常 ≤300 字；超出时说明任务复杂度需要升级到复杂系统型，与用户确认。

## 复杂系统型：六层分层结构
1. **系统身份与使命**：角色、服务对象、核心目标；一句话能回答「这个系统为谁解决什么问题」。
2. **能力与边界**：明确「不做什么」；每个边界配越界时的应答策略（拒绝话术或降级路径），不留「模型自行发挥」的空档。
3. **工作流**：分步指令——输入分类 → 分支处理 → 收尾校验；每步有明确触发条件（什么输入走这条分支）；分支互斥或写明优先级。
4. **规则与约束**：风格、格式、安全分区分条；规则条目带编号（「规则 3.2」）便于测试记录回溯；必须含优先级仲裁——规则冲突时谁覆盖谁（如「安全规则 > 输出格式 > 风格偏好」）。
5. **示例**：few-shot 至少一正例一边界例，覆盖典型与易错输入；示例与规则逐条对得上（示例是隐含规则）。
6. **输出契约**：格式模板 + 异常/降级输出格式（无法满足主格式时输出什么，如错误 JSON 结构或明确的降级声明）。

## 示例与思维链设计
- few-shot 示例的选取：覆盖最常见的典型输入、最容易出错的边界输入；示例的行为必须与规则一致，冲突时先修冲突再交付。
- 思维链引导：复杂推理任务可在工作流中要求「先列要点再作答」或给出推理步骤模板；注意推理过程是否要出现在输出中须明确（可见/仅内部/不要输出），不写死目标模型的私有推理特性，作为需求澄清项记录。
- 示例数量克制：示例占上下文预算，按目标模型上下文长度权衡（记入 01-需求/）。

## 反模式清单（起草与诊断时逐条过）
- **约束自相矛盾**：「详细展开」+「50 字以内」——两条约束放在一起必有一个失效。
- **否定式指令堆砌**：「不要…不要…」连用——改为正向要求（「使用书面语」而非「不要口语」）。
- **强调替代结构**：「请务必」「非常重要」连用却不给明确步骤与格式——模型行为仍不可预期。
- **指令稀释**：与核心任务无关的规则混入——总长度与规则数失控，核心指令权重被稀释。
- **示例与规则冲突**：规则说「仅输出 JSON」，示例却带解释性文字——示例是隐含规则，冲突时行为不可预期。
- **输出格式不确定**：只说「格式清晰」不给字段/模板——每处输出格式都必须确定到结构层级。
- **空话式约束**：「表现好一些」「更专业一点」单独充当约束——不可核验，须落到具体动作。
- **边界无策略**：只定义正常路径，越界输入行为靠模型自行发挥——每个边界配应答策略。
- **需求假设写死**：把模型型号、上下文长度、可用工具直接写死在提示词里而不核对需求契约——与 01-需求/ 契约不符即返工。

## 通用提示词与 DSH 元层面的结构差异
- 通用提示词的「读者」是目标模型；DSH 元层面的「读者」是 DSH Loader 与运行时，结构单位是行（row）而不是段落——格式协议（bundle 的 cordis.patch.yml 声明行 / SKILL.md）、realm 规则与挂载验证纪律见 dsh-preset-craft。
- 两者共通的纪律：结构分层清晰、条目可引用、示例与规则一致、边界有策略。

## 注意事项
- 结构选型（简单指令型 lite / 复杂系统型 system / DSH 元层面）依据需求契约与 `规范-提示词.md`，不凭习惯；篇幅红线（≤300 字）是升级到 system 的信号。
- 设计取舍（为什么选这个结构、为什么这样分层）写进 02-设计/，供修改阶段回溯。
- 本 skill 是方法论，不是规范事实源：与 `规范-提示词.md` 或用户自备规范冲突时，以规范文档为准。
