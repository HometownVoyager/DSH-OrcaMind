# 提示词项目搭建（prompt-project-bootstrap）

## 何时使用
- 用户提出新的提示词撰写需求、且尚未建立项目目录时（先与用户确认需求边界与使用场景，再执行本 skill）。
- 用户要求「开新项目」「建提示词项目」「写系统提示词/指令提示词/DSH 预设或 skill」时。
- 每轮对话开始检阅项目状态、每阶段结束时更新进度与确认记录。
- 接手已有项目但缺 README.md 时：先按本 skill 模板补建（已有内容照实填入，不确定处标注待确认），再展开工作。
- DSH 元层面项目同样用本 skill 建目录与登记，类型登记为「DSH 元层面」，流程按 dsh-preset-craft 执行。

## 执行顺序（本 skill 是每个项目第一步）
1. **开工规范检查**（先于目录搭建或同步进行）：检查工作区主目录的 `规范-提示词.md`——
   - 存在用户提供的结构/格式规范且完整 → 直接采用，不再询问；
   - 没有、不全，或与默认规范冲突 → 停下询问，给三个方向由用户选：① 选默认集（简单指令型 spec-prompt-lite / 复杂系统型 spec-prompt-system；DSH 元层面项目默认按 dsh-preset-craft 的格式协议执行，同时向用户确认）；② 新放一份（用户自备规范文档或目标平台官方提示工程指南，可等待放入工作区后继续）；③ 由 agent 当场起草（用 web_search 检索、用 web_fetch 打开原文核对），草稿经用户逐条确认后定稿。
   - 选定后落盘 `规范-提示词.md`（统一四节骨架）：①来源记录（规范集名称、出处与定稿日期）②结构与目录约定 ③产出格式规范（分层结构、编号体系、示例与输出契约格式）④红线与禁忌。选默认集时汇总引用对应 spec skill 的定稿要点，不复制全文。
   - 用户自备规范不全时，在其基础上按所选默认集补全，补全内容标注并经用户确认后并入。
2. **需求澄清访谈**：按「需求澄清访谈清单」逐项与用户确认，写入 01-需求/需求契约-<名称>.md；不臆测，确认后才冻结契约。
3. **提示词登记**：每条提示词登记名称、类型（简单指令型/复杂系统型/DSH 元层面）、当前版本、状态与测试基线，写入 README 提示词清单表。
4. **目录搭建**（结构如下）。
5. **提示下一步**：每条提示词从「结构设计」阶段开始（prompt-patterns 或 dsh-preset-craft），随后草稿 → 测试与迭代 → 交付与版本记录。

## 需求澄清访谈清单（逐项确认，不臆测）
- 目标模型与上下文长度（决定结构与示例预算）；
- 部署环境与可用工具（是否有联网/代码执行/文件访问等）；
- 使用方式：单轮调用、多轮对话，还是系统提示词常驻；
- 输入输出契约：输入形态（文本/结构化数据）、期望输出格式（自由文本/JSON/模板）、异常输入的期望行为；
- 语言与受众（中文/英文，面向谁使用）；
- 评测期望：怎样算「好」（准确性/格式符合/风格），已知边界情况与历史踩坑；
- DSH 元层面项目另加：新写还是派生改造、派生源、id 与显示名、是否触及现有预设（触及须用户拍板）。

## 标准目录结构
每个项目一个目录，位于当前工作目录（或用户指定的目录）下，命名为项目名（用户确认的暂定名即可）：

```
<项目名>/
├── README.md                    # 项目总览：提示词清单表、当前阶段、确认记录（最先创建，每轮先读）
├── 01-需求/                     # 需求契约-<名称>.md（逐项访谈记录 + 冻结状态 + 变更记录）
├── 02-设计/                     # 设计-<名称>.md（结构选型、逐层设计要点、设计取舍说明）
├── 03-提示词/
│   ├── 当前版/                  # <名称>-v<n>.md（文件头：版本号/变更摘要/日期）
│   └── 历史版本/                # 只增不改，重大变更另存新文件
├── 04-测试/
│   ├── 用例集.md                # 边界用例与评估标准（正常/越界/对抗/空输入四类）
│   └── 测试记录.md              # 每版测试结果（追加式：版本/用例/结果/未通过项与处置）
└── 05-交付/                     # 交付说明与使用指南（交付三件套索引）
```

说明：
- 目录名带数字前缀是为了排序稳定；工作流按 需求（01）→ 设计（02）→ 草稿与版本（03）→ 测试（04）→ 交付（05）单向推进。
- 03-提示词/历史版本/ 下的任何文件不可覆盖修改；发现误改历史版本须立即告知用户并恢复。
- 全部文件使用 Markdown、UTF-8 编码，标题层级从 `#` 开始。

## README.md 模板
```markdown
# <项目名>

- 项目说明：<一句话，本项目收哪些提示词>
- 规范集：<规范-提示词.md 所选规范集名称>（见工作区 规范-提示词.md）
- 当前阶段：<需求澄清 / 结构设计 / 草稿 / 测试与迭代 / 交付与版本记录>
- 当前状态：<一段话说明各条提示词推进到什么程度>
- 下一待确认事项：

## 提示词清单表
| 名称 | 类型 | 当前版本 | 状态 | 测试基线 | 备注 |
|------|------|----------|------|----------|------|

## 阶段确认记录
| 日期 | 提示词 | 阶段 | 确认内容 | 用户裁决 |
|------|--------|------|----------|----------|

## 进度记录
| 日期 | 完成内容 | 文件 |
|------|----------|------|
```

## 需求契约-<名称>.md 模板
```markdown
# 需求契约：<提示词名称>

- 状态：<澄清中 / 已冻结（日期） / 变更中>
- 目标模型与上下文长度：
- 部署环境与可用工具：
- 使用方式：<单轮 / 多轮 / 系统提示词>
- 输入输出契约：<输入形态 → 期望输出格式；异常输入行为>
- 语言与受众：
- 评测期望：<怎样算好；已知边界情况>
- 调研记录：<web_search 所得要点与来源链接，注明事实与建议>
- 变更记录：
| 日期 | 变更内容 | 影响（是否需重跑测试基线） | 用户确认 |
|------|----------|------------------------------|----------|
```

## 执行步骤
1. 与用户确认项目名（暂定即可）、提示词清单、各条类型与使用场景；不确定先求证，不凭空假设。
2. 执行开工规范检查并落盘 `规范-提示词.md`（见上）。
3. 逐项执行需求澄清访谈，落 01-需求/；契约经用户确认后标记「已冻结」。
4. 创建目录与骨架文件：README.md 最先创建并填写已知信息；子目录创建后可各放一个索引文件说明用途。
5. 接手已有项目补建时，README 与清单表按现有内容照实填写，无法确认的条目标注「待确认」并列入下一待确认事项，不凭空补写。
6. 搭建完成后，把项目目录路径与结构告诉用户，并说明下一步（结构设计）。

## 注意事项
- 不要在没有项目目录的情况下把提示词写进零散文件——版本管理、测试基线与交付核查都依赖这个结构。
- 每轮工作以 README.md 为入口：有则先读再干活，无则先建再干活。
- 同一项目多条提示词时，每条独立走完五个阶段；不同提示词的需求契约、设计与版本文件以名称区分，不混放。
- 用户已有自己的目录习惯时尊重用户结构，但至少保证 README 与五个子目录可被找到。
- 规范-提示词.md 是唯一规范事实源：修改规范须先经用户拍板并同步更新该文档。
