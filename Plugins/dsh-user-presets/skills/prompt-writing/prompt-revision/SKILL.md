# 提示词修改与定稿（prompt-revision）

## 何时使用
- 测试未通过项的修改：按测试记录的未通过原因逐项修正时。
- 用户反馈驱动的修改：需求契约微调、风格调整、示例替换时。
- 交付与版本记录阶段：定稿前做三件套核查与版本核查时。
- 需求契约变更后：评估修改面、重跑基线、更新版本时。

## 逐轮修改流程
1. **定修改面**：先读测试记录与用户反馈，列出本轮要修的条目（编号对照用例与规则条目）；未列入的条目不动。
2. **改设计留痕**：涉及结构或约束层面的修改，先在 02-设计/ 的设计文档追加「变更记录」，再动提示词正文。
3. **新版本文件**：重大变更（结构、工作流、输出契约、约束增删）在 03-提示词/当前版/ 另存 `<名称>-v<n+1>.md`，文件头写版本号、变更摘要、日期；微调（错字、标点、示例措辞）可就地修改当前版、在变更摘要补记，并重跑该版基线后在测试记录中留痕。
4. **重跑基线**：按 prompt-testing 执行——先跑未通过用例，再全量重跑；结果追加测试记录。
5. **同步登记**：更新 README 清单表的当前版本与状态，追加进度记录。

## 版本管理核查表
| 核查项 | 判据 |
|---|---|
| 版本头齐全 | 当前版文件头含版本号、变更摘要、日期三要素 |
| 历史版本未覆盖 | 03-提示词/历史版本/ 的文件与交付过的版本逐字一致（发现误改立即告知用户并恢复） |
| 版本号连续 | 当前版版本号 = 历史版本最大号 + 1（跳号须在变更摘要说明） |
| 变更可追溯 | 每次变更在变更摘要与测试记录中都能对上日期与内容 |
| 契约同步 | 需求契约变更已在 01-需求/ 留变更记录，且测试基线已相应修订 |

## 交付三件套核查
| 件 | 判据 |
|---|---|
| 提示词正文 | 所选规范的结构要素齐全（lite 四段 / system 六层 / DSH 元层面格式协议）；规则条目可引用；示例与规则无冲突；反模式清单逐条过 |
| 用例集 | 四类用例覆盖到位（lite 轻量集按 prompt-testing 分级）；评估标准可判定；与最新需求契约一致 |
| 测试记录 | 当前版本号有完整基线记录；无未通过项未处置；静态审查与实测分别标注，不以静态审查冒充实测 |

三件套之外，交付说明落 05-交付/：使用指南（如何接入、系统提示词放置位置或调用方式）、版本历史索引、已知限制与边界行为说明。

## 定稿判定四条件
同时满足才可请用户确认定稿：
1. **基线全过**：当前版本完整基线通过，测试记录无悬置未通过项；
2. **规范核查通过**：按 `规范-提示词.md` 逐项核对结构与格式，红线禁忌零触犯；
3. **三件套齐全**：正文 + 用例集 + 测试记录齐备且版本号一致，交付说明落盘；
4. **用户确认**：以上三条汇报后，用户明确确认定稿——确认记入 README 阶段确认记录。

## 注意事项
- 不擅自推翻已确认契约：用户反馈与已冻结契约冲突时，先指出冲突请用户裁决，再改契约、再改提示词。
- 定稿后修改即新版本：定稿版本的任何后续修改走「另存新版本 + 重跑基线」，不在定稿文件上覆盖。
- 每轮修改收尾更新 README：清单表状态（测试中/待定稿/已定稿）与阶段确认记录，保证下轮 Read 能还原进度。
