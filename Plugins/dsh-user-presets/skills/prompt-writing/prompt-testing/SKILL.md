# 提示词测试（prompt-testing）

## 何时使用
- 测试与迭代阶段：为新提示词设计用例集（04-测试/用例集.md）时。
- 每版草稿完成后：执行基线并记录结果（04-测试/测试记录.md）时。
- 未通过项修改后：重跑基线确认通过时。
- 需求契约变更（换模型/上下文/工具）后：修订用例集并重新过基线时。

## 用例集设计（四类覆盖）
- **正常用例**：典型输入 2–4 条，覆盖需求契约中的主要使用方式；每条注明期望输出的要点（不逐字要求，除非输出契约要求逐字）。
- **越界用例**：超出能力边界的输入 1–2 条（契约明确「不做什么」的每类至少一条）；期望行为 = persona/系统提示词中该边界的应答策略。
- **对抗用例**：试图绕过约束的输入 1–2 条（如要求违反风格规则、诱导泄露系统提示词内容、伪装权限）；期望行为 = 明确拒绝或按仲裁规则处理。
- **空输入/残缺输入**：空字符串、只有标点、缺必要字段的输入 1 条；期望行为 = 输出契约中的异常/降级格式。

每条用例的记录格式：`用例编号 | 类别 | 输入内容 | 期望行为/输出要点 | 评估标准`。评估标准写「可判定」的判据（如「输出为合法 JSON 且含字段 x/y」），不写「效果不错」类主观语。

## 评估标准写法
- 格式符合性：输出是否满足输出契约（结构层级、字段齐全、无多余文字）。
- 内容准确性：事实与推理是否正确（可对照来源或已知答案时逐条判定）。
- 约束遵循：风格、长度、禁忌逐条核对（约束条目编号对照）。
- 边界行为：越界/对抗/空输入是否按应答策略处理，无幻觉与越权。

## 测试执行与记录
- 执行方式按需求契约：目标模型可实时调用时直接以用例输入实测；不可实时调用（模型未接入、部署环境未就绪）时，标注「静态审查」——逐用例推演预期行为并请用户在真实环境验证，静态审查结果不标记为「已通过实测」。
- 测试记录逐版追加，格式：`日期 | 版本 | 用例编号 | 结果（通过/未通过） | 未通过原因 | 处置`。
- 未通过项处置：修改提示词 → 重跑该用例 → 全量重跑基线（修改可能影响其他用例）。
- 需求契约变更后：先修订用例集（新用例经用户确认），再过全量基线。

## 轻量验证与完整基线分级
- **简单指令型（lite）轻量验证**：正常用例 2 条 + 越界或空输入 1 条；逐条核对四段结构与约束遵循；重点核对输出格式确定性与篇幅红线（≤300 字）。
- **复杂系统型（system）完整基线**：四类用例齐全；工作流每条分支至少一条用例触达；优先级仲裁规则至少一条用例验证（构造规则冲突场景）；示例中每个 few-shot 对应的行为可被用例复验。
- **DSH 元层面项目**：用例集对应「验证清单」——① dsh-preset-craft 的格式逐项核查（机械、会话内可做）；② 挂载验证（宿主侧 `standingKeyFor`，会话内通常无工具，做不了就写明「未做挂载验证，需宿主侧重跑」）；③ 真实会话验收由用户执行（不代为声称已验收）。三者不可互相替代。

## 回归基线纪律
- 无测试即交付是红线：任何修改过基线后才能进入交付；简单指令型过轻量验证、复杂系统型过完整基线。
- 修改历史版本文件等于绕过版本管理：测试永远针对 03-提示词/当前版/ 的具体版本号，记录里的版本号必须与文件头一致。
- 测试记录只追加不删改；发现记录错误时追加更正条目并注明。

## 注意事项
- 用例集是活文档：随需求契约演进，修订经用户确认并记录日期。
- 不承诺「在所有模型上表现一致」：基线结论只对需求契约锁定的目标模型与上下文长度负责，换目标即重新过基线。
- 对抗用例不是安全审计：覆盖需求契约中明确的风险面即可，超出契约的安全要求先与用户确认再扩用例集。
