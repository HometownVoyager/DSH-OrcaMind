# 简单指令型提示词规范（spec-prompt-lite，定稿版 2026-09-10）

> 用途：开工规范检查选默认集「简单指令型」时，本 skill 是 `规范-提示词.md` 的内容母本（四节骨架、写法通则与执行要求的纳入方式见 spec-common；落盘时记录来源为「本预设默认集·简单指令型（2026-09-10 定稿）」）；简单指令型提示词的设计、起草与校对阶段随时对照执行。目标平台有官方提示工程指南且要求更具体时，以其为最高优先级。

## ① 来源记录
- LLM 提示工程通用最佳实践（Microsoft Learn 提示工程模块、社区提示模式目录等综合整理）；
- 定稿时间：2026-09-10（据检索摘要提炼，用户确认定稿）。

## ② 结构与目录约定
- 四段轻量结构：**角色**（一句身份定义，如「你是一位资深技术文档译者」）→ **任务**（一句动词开头的可执行指令，含交付物）→ **约束**（3–6 条：范围、风格、长度、禁忌）→ **输出格式**（明确到结构层级或模板示例）。
- 适用场景：单轮任务、一次性指令、内嵌到应用的单点调用（分类、改写、摘要、翻译等）。
- 项目目录按「版本与测试档案制」（prompt-project-bootstrap）：01-需求/ 02-设计/ 03-提示词/（当前版 + 历史版本）04-测试/ 05-交付/；本套提示词通常单文件即可交付。

## ③ 产出格式规范
- 指令正向表述（「使用简体中文书面语」而非「不要用口语」）；每段职责单一，不混杂。
- 输出格式要么给字段清单、要么给一个最小示例，二选一；需结构化输出时明确「仅输出 JSON，不要任何多余文字」。
- 篇幅控制：简单指令型整体通常 ≤300 字；超出即说明任务复杂度需要升级到复杂系统型。

## ④ 红线与禁忌
- 禁止约束自相矛盾（如「详细展开」+「50 字以内」）；禁止一次塞入多个独立任务。
- 禁止否定式指令堆砌（「不要…不要…」连用）——改为正向要求。
- 禁止依赖「请务必」「非常重要」式强调替代清晰结构；禁止给模型留下输出格式的不确定空间。
- 禁止把用户数据假设写死（模型/上下文长度/可用工具作为需求澄清项记录在 01-需求/，不臆测）。

## 执行要求（写入 规范-提示词.md 时随结构节一并纳入）
- 起草前需求契约未经确认的，不得进入草稿；每条约束须可核验（能回答「做到了是什么样、没做到是什么样」），禁空话式约束（「表现好一些」「更专业一点」单独出现即不合格）。
- 交付阶段按 prompt-revision 核查：四段齐全且职责单一、约束无矛盾、输出格式确定、篇幅 ≤300 字（超出时与用户确认升级为复杂系统型）、文件头版本信息齐全。
