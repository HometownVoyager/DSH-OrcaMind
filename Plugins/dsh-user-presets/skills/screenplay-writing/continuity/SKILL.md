# 连续性管理（continuity）

## 何时使用
- 每次开始写作前（快速核查本段涉及的设定与上段的衔接，先对 anchors.md 定向核对本段涉及的年龄/称谓/信物/空间）。
- 每完成一批段落后（登记新事件、更新 scene-list.md）。
- 每阶段产出落盘前（全量核查一次，锚点矩阵优先）。
- 修改设定后（检查对已写正文的影响面，含锚点变更的全文影响排查）。
- 用户指出"前后矛盾""穿帮"时（定位并请用户裁决）。

## 核查顺序（锚点矩阵优先，定向靶向核查）
从"全文模糊搜"升级为"锚点矩阵核验"：先对 `00-设定/anchors.md` 做**定向靶向核查**，再按需展开全文检索。顺序如下：
1. **锚点核验**：对照 anchors.md 四节，核查本次产出涉及的角色年龄与关键节点、称谓三层口径（Speaker ID / 旁白称谓 / 对白呼告）、信物与体态状态、空间拓扑与动线，逐项比对出现处上下文。
2. **关联基准核验**：对照 timeline.md、scene-list.md、glossary.md 与设定集，核查事件日期序列、FLAG 与分支、专有名词。
3. **全文模糊检索（兜底）**：仅在前两步无法定位矛盾时才用检索工具全局搜索关键名/术语，对比出现处的上下文。
4. 正文中出现的新事实反向补录进基准（涉及锚点变更的先请用户确认）。

## 检查清单
1. **锚点·年龄与时间**：各角色当前年龄与关键节点年龄是否符合 anchors.md 年龄矩阵；年月日、季节、昼夜、经过天数是否自洽（对照 timeline.md）；生日、成人礼、学段交替处重点核查——这是"16岁与18岁混淆"的高发区。
2. **锚点·称谓三层**：说话人标签（Speaker ID）、旁白认知称谓、对白呼告三者是否与 anchors.md 称谓网格一致——系统标签、叙述称谓与口语称呼各归各层，不得混用或前后打架。
3. **锚点·核心资产与体态状态机**：重要道具从哪来到哪去、当前佩戴/持有者是谁、所处阶段（对应 Day/章节节点）是否与 anchors.md 状态机一致，别凭空消失、凭空出现或状态回跳；角色不可变体貌（发型/发色/瞳色）是否偏离体貌锚点。
4. **锚点·空间拓扑**：上下楼方式（电梯/步梯）、房间位置、门窗朝向、视线与声音遮挡是否符合 anchors.md 空间拓扑；同一场景内的道具、服装、光线、桌面状态、门窗位置跨段一致。
5. 段落衔接：上一段结束时的人物位置/状态，与下一段开场是否一致（出场/退场、情绪、随身物品）。
6. 人物状态：伤势、能力、情绪基线、关系变化。
7. 大纲与设定：事件序列是否符合世界观规则与角色动机；剧情大纲是否只含抽象层级内容（无场景/台词/演出指令）。
8. FLAG 与分支：选项后果、FLAG 变化与 scene-list.md、结局条件一致；分支合并后角色状态、道具与情报无矛盾。
9. 时间线与名词：新事件与专有名词以 timeline.md 与 glossary.md 为基准登记。
10. 跨章台账：本轮章的章号、剧内时间点、地点、出场角色、章节末状态、FLAG 与伏笔变化是否与 `03-修订/chapter-state.md` / `03-修订/foreshadowing.md` 已登记内容一致，且已按「每章强制同步项」同步更新。

## 方法
- 每次核查先读 `00-设定/anchors.md`（基准事实层），再读本轮涉及的其他基准文件；锚点核验通过后，用检索工具做针对性抽查与兜底。
- 以 anchors.md、设定集、timeline.md 与 scene-list.md 为基准；正文中出现的新事实反向补录进基准（涉及锚点变更的先确认）。
- 跨章长线内容（伏笔、事件链、FLAG 后果）在 continuity-log.md 的"追踪事项"小节单独登记。

## 长篇跨章状态台账（2026-11-13 增强）
长篇单会话写作不能只靠对话记忆。除上述定向核查外，强制维护两份台账（新项目时随 `03-修订/` 一起建）：
- `03-修订/chapter-state.md`：每章一行，登记「章号 / 剧内时间点 / 地点 / 出场角色 / 各角色章节末状态（伤势·情绪·关系·随身物品）/ FLAG 变化 / 埋设与兑现的伏笔 / 选项与分支指向」。写完每章立即追加；动笔写下一章前必读最近 3 章行。
- `03-修订/foreshadowing.md`：每条伏笔一行，登记「伏笔 / 埋设章 / 计划兑现章 / 状态（未回收·已兑现·已废弃）/ 关联 FLAG 与分支」。每章动笔前过一遍「未回收」清单，兑现或废弃当场改状态；钩子必须兑现。
- **每轮必读最小集**：`00-设定/anchors.md` 四节 + `chapter-state.md` 最近 3 章行 + `foreshadowing.md` 未回收清单 + 结局清单（`01-规划/endings.md`，接手 vn-design 项目时为 `02-系统/endings.md`）+ 上一章正文结尾段。未复读部分在报告里如实说明。
- **每章强制同步项（同轮完成，不拆到下一轮）**：`02-剧本/draft-vN/scene-list.md`、根 `剧情精述.md` 对应章精述、`chapter-state.md` 该章行、`foreshadowing.md` 受影响伏笔状态、continuity-log.md 追踪事项。任一缺漏不算本轮完成。
- **跨章衔接核查**：Check 步按 chapter-state.md 核对本轮章与最近 3 章「章节末状态 → 下章开场」是否一致（出场/退场、伤势、情绪基线、随身物品、地点、剧内时间），按 foreshadowing.md 核对到期伏笔是否兑现；冲突先请用户裁决，不自行改写已确认章节。
- 章号 `ch001` 三位递增、分支 `ch001-2a / -2b`；chapter-state.md 每章有且仅有一行，断号重号先停下核对。

## 冲突处理
1. 正文与 anchors.md/设定集/大纲不一致、且该正文尚未经用户确认时，以 anchors.md 与设定集为基准修改正文（接手 vn-design 项目时，设定与大纲以项目既有的 vn 体系文件为准），并在记录中说明；正文已经用户确认的冲突按第 2 条请用户裁决。
2. 冲突涉及 anchors.md 本身、已确认设定、关键剧情走向，或两种口径各有依据时，先指出冲突并说明双方口径的来源，请用户裁决，不得自行改写已确认内容与锚点。
3. 裁决或修复后必须在 continuity-log.md 记录：日期、冲突内容、裁决结果、修改了哪些文件；锚点变更必须额外记录"改了什么、为什么、何时"。
4. 批量改名/改设定时：先检索全部出现位置，列出改动清单，经用户确认后逐处执行，最后全局复查一遍。

## continuity-log.md 格式（03-修订/continuity-log.md；接手 vn-design 项目时沿用该项目既有文件，不新建第二份）
```markdown
# 连续性记录
## <日期>
- 查证：<冲突内容，如第 8 章与第 15 章季节不一致>
- 裁决：<以谁为准、为什么>
- 修改：<改动的文件清单>

## 追踪事项
- <伏笔/事件链/FLAG 后果，标注所在章节>
```
