# 视觉小说剧本项目搭建（vn-script-project-bootstrap）

## 何时使用
- 用户提出创作新剧本（VN/GalGame）且尚无项目目录时。
- 用户要求"新建剧本项目""开新剧本"时。
- 每轮对话开始检阅项目状态、每阶段结束时更新进度与确认记录。
- 接手已有项目但缺少 README.md、剧情精述.md 或 anchors.md 时：先按本 skill 模板补建（已有内容照实填入，不确定处标注待确认），再展开工作。

## 标准目录结构
```
<项目名>/
├── README.md                  # 项目概览：一句话故事、当前阶段、阶段确认记录（最先创建，每轮先读）
├── 剧情精述.md                # 当前写作进度 + 全部已有剧情的逐章/逐线精述（比 README 详细）
├── 00-设定/
│   ├── anchors.md             # 全局基准事实层（Anchors Layer）：年龄矩阵/空间拓扑/称谓网格/核心资产与体态状态机（最先落盘，先于正文，连续性核查第一基准）
│   ├── world.md               # 世界观：规则/历史
│   ├── characters/            # 角色档案，每人一个文件
│   │   └── relationships.md   # 人际关系网与变化方向
│   ├── factions.md            # 势力与组织（与小说预设同粒度，从 world 拆出）
│   ├── geography.md           # 地理与地点
│   ├── timeline.md            # 剧内时间线
│   ├── glossary.md            # 专有名词表
│   ├── style.md               # 剧本文风：基调、类型惯例、禁忌
│   └── inspirations.md        # 灵感与素材库（考据来源、参考作品、待用桥段）
├── 01-规划/
│   ├── logline.md             # 一句话故事与卖点
│   ├── treatment.md           # 故事梗概（含结局方向）
│   ├── structure.md           # 结构与节拍：共通线/个人线、章节功能、选项节奏
│   ├── outline.md             # 剧情大纲（仅抽象层级，禁止场景与台词）
│   ├── endings.md             # 结局清单与达成条件、优先级（自建多结局项目必建；接手 vn-design 项目时以既有 02-系统/endings.md 为结局单一事实源，不建本文件——见「接手 vn-design 项目的衔接契约」）
│   └── character-voices.md    # 声音档案
├── 02-剧本/
│   └── draft-v1/              # 每稿一个目录
│       ├── ch001.md …         # 逐章剧本（VN 脚本格式，含演出指令与选项分支），三位编号
│       └── scene-list.md      # 段落/场景表
└── 03-修订/
    ├── continuity-log.md      # 连续性核查与冲突裁决记录
    ├── chapter-state.md       # 跨章状态台账：每章一行（章节末状态/FLAG/伏笔/分支）
    ├── foreshadowing.md       # 伏笔与 FLAG 台账：埋设/兑现章与当前状态
    └── revision-log.md        # 修改记录与复盘
```

## 全局基准事实层（anchors.md）——脚手架最优先落盘的文件

`00-设定/anchors.md` 是本项目**不可变基准事实层**：把最易发生"事实漂移"的常量（年龄、空间、称谓、信物）集中成单一事实源，编写与确认**优先于任何篇章正文**，此后一切连续性核查以它为第一基准。它在设定集阶段随各文档逐步填实，但在动笔写正文前必须全量确认并锁定。

### 搭建纪律
1. 创建目录骨架时**立即**生成 `00-设定/anchors.md`，用下方四节模板搭好结构，已确认的事实照实填入，未确认处标注「待确认」。
2. 设定集阶段结束（进入结构与节拍之前）必须完成 anchors.md 全量填写并经用户确认；此后视为**基准事实**，正文只读不写。
3. 正文写作中发现需要改锚点的（如改年龄、改空间），必须先请用户裁决，再改 anchors.md，并在 `03-修订/continuity-log.md` 记录"改了什么、为什么、何时"，最后排查已写正文（见 continuity skill）。

## 段落/场景表（scene-list.md）
记录每个段落：章号/段落号、地点、时间、出场角色、内容一句话、选项与分支指向、FLAG 变化——这是连续性核查与篇幅估算的基础。新场景/新地点出现时，先核对 anchors.md 的空间拓扑是否已收录；未收录的空间先补录 anchors（经用户确认）再写正文。

## 剧情精述.md（写作进度与既有剧情精述）
README 的进度栏只记状态，本文件记录细节，是每轮动笔前回顾全部既有剧情的主要依据：
- **当前写作进度**：写到第几章/第几条线/第几稿、最近一次修订轮次、正在处理的段落（比 README 具体，如「第 8 章 2a 分支初稿完成，选项跳转待接」）。
- **逐章剧情精述**：每章一条（按章号排列；分支章按分支分别记），用复合句完整概括该段剧情发生了什么、角色状态与关系如何变化、揭示与埋设了哪些信息、FLAG 与选项走向；可独立读懂，不引用台词原文。
- **待兑现伏笔与 FLAG**：未回收的伏笔、未触发的 FLAG 与分支汇合点清单，与 `03-修订/continuity-log.md` 的追踪事项保持一致。

更新纪律：每写完一章（或一个分支段）或完成一次修订，立即追加或更新对应条目与进度状态；回溯修改剧本时同步改写受影响章的精述。精述与剧本或已确认内容不一致时，以剧本与已确认内容为准并当场修正精述。

## 长篇跨章台账（与 continuity skill 配套，2026-11-13 增强）
本预设是单会话写完整部剧本的模式，除 anchors.md 基准事实层外，另用两份台账锁住跨章状态，避免「写到第 N 章忘了第 2 章」：
- `03-修订/chapter-state.md`：每章一行，登记「章号 / 剧内时间点 / 地点 / 出场角色 / 各角色章节末状态（伤势·情绪·关系·随身物品）/ 本章 FLAG 变化 / 本章埋设与兑现的伏笔 / 选项与分支指向」。写完每章立即追加；动笔写下一章前必读最近 3 章行。
- `03-修订/foreshadowing.md`：每条伏笔一行，登记「伏笔 / 埋设章 / 计划兑现章 / 状态（未回收·已兑现·已废弃）/ 关联 FLAG 与分支」。每章动笔前过一遍「未回收」清单，兑现或废弃当场改状态。
- **每轮必读最小集**：anchors.md 四节 + chapter-state.md 最近 3 章行 + foreshadowing.md 未回收清单 + 结局清单 + 上一章正文结尾段。未复读部分在报告里说明，不假装已通读。
- **每章强制同步项（同轮完成）**：scene-list.md、剧情精述.md 对应章精述、chapter-state.md 该章行、foreshadowing.md 受影响伏笔、continuity-log.md 追踪事项。缺一不算本轮完成。
- 章号 `ch001` 三位递增、分支 `ch001-2a / -2b`，chapter-state.md 每章有且仅有一行；断号重号先停下核对。

```markdown
# <项目名>

- 类型/平台目标：<如 恋爱 ADV / PC / 预计游玩时长 10-20 小时>
- 一句话核心创意：
- 当前阶段：<创意与 logline / 设定集 / 结构与节拍 / 剧情大纲 / 剧本正文 / 修订定稿>
- 当前进度：第 <n> 章｜第 <k> 条线｜第 <v> 稿

| 日期 | 阶段 | 确认内容 | 用户裁决 |
|------|------|----------|----------|
```

## 执行步骤
1. 与用户确认项目名（暂定）、类型（恋爱/悬疑/剧情等）、篇幅（章节数、预估字数与游玩时长）、文风偏好（基调与可参照作品）、是否已有系统设计（分支/好感度/结局条件）与目标引擎——这些决定后续结构与篇幅基准，也是此后各阶段判定文风的依据。
2. 创建目录骨架与 README、剧情精述.md 两份根文档，**并立即生成 `00-设定/anchors.md`（四节模板，已确认事实照实填入）**；其余规划文件先只写占位，按阶段推进逐份补全。
3. 接手已有项目补建时，README、剧情精述与 anchors 按现有剧本与设定照实填写，无法确认的条目标注「待确认」并列入下一待确认事项，不凭空补写。
4. 建议下一步：从 logline 开始（01-规划/logline.md），设定集可并行推进；设定集阶段内完成 anchors.md 全量填写并经用户确认。

## 注意事项
- 阶段顺序为 创意与 logline → 设定集 → 结构与节拍 → 剧情大纲 → 剧本正文 → 修订定稿；只有用户确认本阶段完成、或明确指示进入下一阶段后才推进，并在 README 阶段确认记录中登记该确认。
- **动笔写正文的前置条件**：anchors.md 已全量填写并确认（基准事实先行），否则先停下补锚点，不带着未锁定的年龄/空间/称谓事实下笔。
- 每轮工作以 README.md 与剧情精述.md 为入口：有则先读再干活，无则先建再干活；anchors.md 每次连续性核查必读（见 continuity skill）。
- 每阶段产出落盘前按 continuity skill 执行一次一致性核查；查出的冲突先请用户裁决，并记入 03-修订/continuity-log.md。
- 用户要求跳转或回溯时照办，但要在 README 与对话中说明跳转对前后阶段可能产生的影响（如先写正文会导致大纲未定而返工）。
- 用户已有自己的目录习惯时尊重用户结构，但至少保证设定集、规划文档、剧本正文与修订记录四部分可被找到。
- 若项目目录来自「视觉小说全栈设计」预设（00-设定/01-规划/02-系统/03-修订/04-资产），沿用其结构、不另建设定与规划目录：以其已确认的设定、大纲与系统设计为基准，剧本正文写入接手时在项目内新增的 05-剧本/ 目录（沿用其编号体系），剧情精述.md 写入项目根目录，并在该项目的 README 确认记录中登记；项目缺 `00-设定/anchors.md` 时按「只增不改」原则补建（属例外），内容从已确认设定照实汇总、不新造事实。
