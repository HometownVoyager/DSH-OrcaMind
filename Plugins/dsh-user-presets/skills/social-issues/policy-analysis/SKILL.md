# 问题定义与根因分析（policy-analysis）

## 何时使用
- B 轨「问题定义与边界」阶段：落盘 问题定义.md。
- B 轨「根因分析」阶段：落盘 根因分析.md。
- A 轨涉及政策背景梳理、B 轨方案设计需要回看根因时复用。

## 问题定义与边界
一个界定清晰的问题定义回答五问，缺一即待确认：
- **是什么**：问题的现象描述与本质概括（现象是观察到的表象，本质是它与什么深层矛盾相连）。
- **不是什么**：边界排除——相近但不属于本问题的问题、容易被混入的相关议题；排除避免方案设计跑偏。
- **影响谁**：利益相关方清单（受影响群体、执行方、监管方、关联方），各自受何影响、影响程度量级。
- **时间与范围**：问题从何时开始、当前处于什么阶段、地域/行业/人群覆盖范围。
- **成功判据**：问题被解决到什么程度算解决（可观察、可核验的判据，供落地路径与复盘引用）。

问题写成陈述句 + 判据句，不写成口号；范围变化（扩大/缩小/转移）须先经用户确认并登记进 README。

## 根因分析路径
**方法论为重心**（定稿纪律）：交付的是可复用的分析路径（框架、步骤、判据），而非只给结论；读者换一个同类问题也能照着走一遍。

1. **症状与根因区分**：症状是可见的表现，根因是产生症状的机制。用「连问五个为什么（5 Whys）」或「因果链拆解」把每条症状追到不能再分解的环节；停在「人们不重视」「制度不完善」类表述即是没追到底。
2. **机制链条完整**：每条根因写成完整链条——「起因 → 传导环节 → 影响对象 → 结果」，环节之间有可指认的因果依据（已核查的事实、政策条文、数据），不凭空假设传导。
3. **问题间关联**：本问题与其他问题的关联（同源、互为因果、竞争资源）；政策链条——相关政策的沿革、现行规定与执行偏差；把问题放进历史脉络与政策链条中考量，不孤立就事论事。
4. **多方面考虑**：利益相关方（谁受益/谁受损/谁执行/谁监管）、上下游环节、短期/长期效应逐一过一遍；检视不到的方面如实标注「待确认」，不得装作已周全。
5. **根因分级**：把根因分为直接原因/深层原因/制度性原因，标注每条的确认状态（已核实/推测待验证）与依据（考据记录编号）。

## 根因分析.md 结构
```markdown
# 根因分析：<问题一句话>
## 一、分析路径（怎么分析的）
- 采用的框架与步骤：<为什么选它>
## 二、症状清单
- <症状1>（依据：考据记录 #n）
## 三、根因链条
- 根因1（直接原因）：<起因 → 环节 → 影响对象 → 结果>（依据：…）
- 根因2（深层原因）：…
## 四、问题关联与政策链条
- 关联问题：…；相关政策沿革：…
## 五、待验证假设与待确认清单
- <假设/未考虑方面>：<验证方式>
```

## 注意事项
- 根因分析是方案设计的地基：根因清单未确认不进方案设计；方案必须逐条对应根因，否则问题分析与对策脱节（spec-report 红线）。
- 区分实证与规范：现状怎么样（实证）与应该怎么样（规范）分开表述，不把价值判断伪装成实证结论。
- 引用数据必须有出处（对照 考据/ 记录）；样本不足以支撑的结论写明置信边界。
- 「高度重视」「进一步完善」「形成合力」类空话不得作为根因或诊断内容。
