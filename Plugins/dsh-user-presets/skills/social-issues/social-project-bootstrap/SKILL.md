# 社会议题项目搭建（social-project-bootstrap）

## 何时使用
- 用户提出新的社会议题写作或问题解决需求、且尚未建立项目目录时（先与用户确认议题与工作轨，再执行本 skill）。
- 用户要求「开新项目」「建议题项目」「搭建方法论研究档案」时。
- 每轮对话开始检阅项目状态、每阶段结束时更新进度与确认记录。
- 接手已有项目但缺 README.md 时：先按本 skill 模板补建（已有内容照实填入，不确定处标注待确认），再展开工作。

## 执行顺序（本 skill 是每个项目第一步）
1. **开工规范检查**（先于目录搭建或同步进行）：检查工作区主目录的 `规范-议题.md`——
   - 存在用户提供的结构/格式规范且完整 → 直接采用，不再询问；
   - 没有、不全，或与默认规范冲突 → 停下询问，给三个方向由用户选：① 选默认集（评论体 spec-commentary / 研究报告体 spec-report）；② 新放一份（用户自备，可等待放入工作区后继续）；③ 由 agent 当场起草（用 web_search 检索权威来源、用 web_fetch 打开原文核对），草稿经用户逐条确认后定稿。
   - 选定后落盘 `规范-议题.md`（统一四节骨架）：①来源记录（规范集名称、出处与定稿日期）②结构与目录约定 ③产出格式规范（标题层级、编号体系、引用/信源标注）④红线与禁忌。选默认集时汇总引用对应 spec skill 的定稿要点，不复制全文。
   - 自备规范不全时，在其基础上按所选默认集补全，补全内容标注并经用户确认后并入。
   - **规范集按轨分列**：A 轨与 B 轨各自选定的规范集必须分开登记（A 轨通常为评论体 spec-commentary，B 轨固定为研究报告体 spec-report）。双轨项目**不强制两轨用同一套规范集**；`规范-议题.md` 的「来源记录」节按轨分列，README 的规范集字段同样按轨分列。只走单轨时另一轨字段写「未启用」。
2. **工作轨判定**：与用户确认本项目走 A 轨（议题文章）、B 轨（问题解决方法论）还是双轨；判定结果登记进 README 的当前轨字段。同一项目只走单轨时，另一轨目录仍建出骨架（空置），便于后续扩展；用户明确不需要时可不建。
3. **目录搭建**（结构如下）。
4. **提示下一步**：A 轨从选题立意开始（argument-craft），B 轨从问题定义开始（policy-analysis）。

## 标准目录结构
每个项目一个目录，位于当前工作目录（或用户指定的目录）下，命名为项目名（用户确认的暂定名即可）：

```
<项目名>/
├── README.md                    # 项目总览：当前轨（A/B）、两轨进度、确认记录（最先创建，每轮先读）
├── 01-议题文章/                 # A 轨
│   ├── 选题立意.md              # 议题、立意与核心判断、由头与现实针对性
│   ├── 考据/                    # 事实核查记录，每条注明信源
│   ├── 论证框架.md              # 论点/论据/反驳预案
│   ├── 成稿/                    # 文章定稿（版本命名 <主题>-v<n>.md）
│   └── 修订记录.md
├── 02-方法论/                   # B 轨
│   ├── 问题定义.md              # 问题与边界（是什么/不是什么/影响谁/范围）
│   ├── 根因分析.md              # 症状与根因区分、分析路径、机制链条
│   ├── 方案对比.md              # 多方案对比与可行性/代价评估
│   ├── 落地路径.md              # 可执行步骤（做什么/谁做/何时/如何验收）
│   ├── 复盘.md                  # 复盘问题清单与判据
│   ├── 考据/                    # 方法论研究的核查记录（政策口径、数据来源）
│   ├── 修订记录.md              # B 轨逐轮修改记录（与 A 轨对称）
│   └── 成稿/                    # 方法论报告定稿（版本命名）
└── 03-共享考据/                 # 两轨共用
    └── 信源库.md                # 跨轨复用的事实底座与信源登记
```

说明：
- 目录名带数字前缀是为了排序稳定；成稿版本文件名用 `<主题>-v<n>.md`，历史版本只增不改。
- B 轨的 `考据/` 与 `成稿/` 是方法论研究的核查记录与报告定稿落点，与 A 轨对称、分开立档。
- 全部文件使用 Markdown、UTF-8 编码，标题层级从 `#` 开始。

## README.md 模板
```markdown
# <项目名>

- 议题：<一句话>
- 当前轨：<A 轨·议题文章 / B 轨·问题解决方法论 / 双轨>
- A 轨规范集：<评论体 spec-commentary / 用户自备规范名 / 未启用>（见工作区 规范-议题.md）
- B 轨规范集：<研究报告体 spec-report / 用户自备规范名 / 未启用>（见工作区 规范-议题.md）
- A 轨阶段：<选题立意 / 事实考据 / 论证框架 / 成文 / 修改定稿>（单轨 B 或未启动时写「未启动」）
- B 轨阶段：<问题定义与边界 / 根因分析 / 方案设计 / 可行性与代价评估 / 落地路径 / 复盘框架>（未启动时写「未启动」）
- 当前状态：<一段话说明两轨各推进到什么程度>
- 下一待确认事项：

## 阶段确认记录
| 日期 | 轨 | 阶段 | 确认内容 | 用户裁决 |
|------|----|------|----------|----------|

## 进度记录
| 日期 | 轨 | 完成内容 | 文件 |
|------|----|----------|------|
```

## 执行步骤
1. 与用户确认项目名（暂定即可）、议题、工作轨与发表/使用场景；不确定先求证，不凭空假设。
2. 执行开工规范检查并落盘 `规范-议题.md`（见上）。
3. 创建目录与骨架文件：README.md 最先创建并填写已知信息；其余骨架文件写入占位标题与简短说明（如 问题定义.md 写「待补充」）。
4. 接手已有项目补建时，README 与各文档按现有内容照实填写，无法确认的条目标注「待确认」并列入下一待确认事项，不凭空补写。
5. 搭建完成后，把项目目录路径与结构告诉用户，并说明下一步（A 轨从选题立意开始，B 轨从问题定义开始）。

## 注意事项
- 不要在没有项目目录的情况下把分析或成稿写进零散文件——后续一致性检查、跨轨复用与进度管理都依赖这个结构。
- 每轮工作以 README.md 为入口：有则先读再干活，无则先建再干活。
- 两轨文件不得混放：A 轨产出只进 01-议题文章/，B 轨产出只进 02-方法论/；跨轨复用的事实与信源先登记 03-共享考据/信源库.md 再引用。
- 信源库.md 的登记格式：每条含 信源名称/日期/链接或出处/核实状态（已核实双源、待核实、存疑）/适用于哪些议题条目。
- 用户已有自己的目录习惯时尊重用户结构，但至少保证 README、两轨产出目录与共享考据三部分可被找到。
