# 方案设计与落地（solution-design）

## 何时使用
- B 轨「方案设计」阶段：设计候选方案并落盘 方案对比.md。
- B 轨「可行性与代价评估」阶段：完成评估并回填 方案对比.md。
- B 轨「落地路径」阶段：选定方案拆解为可执行步骤，落盘 落地路径.md。
- B 轨「复盘框架」阶段：落盘 复盘.md。

## 方案设计
- **以根因为锚**：每个方案逐条对应 根因分析.md 的根因清单；对应不上的方案说明偏离，须说明为何仍值得做（如处理症状的过渡措施）或放弃。
- **实质差异**：2-3 个候选方案必须在机制上有实质差异（作用环节不同、依赖主体不同、代价结构不同），不是同一方案的三种说法；差异本身就是给用户的选择空间。
- **机制说明**：每个方案写清作用机制——通过什么环节改变什么行为/状态，为什么这样能缓解根因；写不出机制的方案是口号。
- **方案缺口处理**：思路不足时发挥主观能动性，给出 2-3 个候选方向并逐一说明依据、代价与收益，请用户拍板后再细化。

## 可行性与代价评估（每个方案四查）
- **执行条件**：需要什么资源、权限、技术、协同方；当前具备哪些、缺哪些。
- **责任主体**：谁来做（具体部门/岗位/机构类型），不得写「相关部门」「有关人员」。
- **成本与收益**：直接成本、间接成本、预期收益与见效周期；收益不确定的写明区间与假设。
- **风险与二阶效应**：执行风险（阻力/失败模式）与二阶效应（方案改变激励后可能引发的新问题）；对策前完成利益相关方检视（谁受益、谁受损、谁执行、谁监管）与时间尺度检视（短期/长期）；检验不到的效应如实标注「待检验」，不得以「影响有限」一笔带过。
- 评估结论落在 方案对比.md 的对比表，推荐排序 + 理由，**选型由用户拍板**。

## 落地路径
- 把选定方案拆解为可执行步骤，每步四要素：**做什么、谁做、何时完成、如何验收**；四要素缺一不可，可核验。
- 「加强」「完善」「进一步」类表述不得单独充当步骤——必须展开为具体动作与责任主体。
- 步骤排序标明依赖关系（哪些可并行、哪些有前置）；给出关键里程碑与总时限。
- 落地路径与复盘判据对应：每个里程碑的验收方式在 复盘.md 有对应判据。

## 复盘框架
- 假设清单：方案设计时的关键假设逐条列出，标注验证方式与验证时点。
- 指标清单：观察哪些指标判断方案是否起效（对照问题定义的成功判据），指标口径注明。
- 触发条件：什么情况下判定方案无效需要调整（阈值 + 观察期）。
- 回看机制：多久复盘一次、由谁主持、复盘结论如何反哺方案修订。

## 方案对比.md 结构
```markdown
# 方案对比：<问题一句话>
## 一、设计依据
- 对应根因：<引用 根因分析.md 根因编号>
## 二、候选方案
- 方案A：<一句话机制> —— 依据/代价/收益/风险与二阶效应/责任主体
- 方案B：…（与 A 机制实质差异点：…）
## 三、对比表
| 维度 | 方案A | 方案B |
|------|-------|-------|
| 执行条件 | … | … |
| 责任主体 | … | … |
| 成本与见效周期 | … | … |
| 风险与二阶效应 | … | … |
## 四、推荐排序与理由（选型待用户拍板）
## 五、待确认与待检验清单
```

## 注意事项
- 禁止建议与分析脱节：每条措施注明所依据的分析条目（根因/评估编号）；不出现无分析支撑的建议。
- 禁止建议空泛到不可执行：任何措施落到具体动作、责任主体与时限。
- 涉及敏感人群的措施考虑匿名化与最小干预；多方案对比时各方案以最强版本呈现，不故意弱化衬托推荐项。
- 选型、范围与优先级变化都须用户拍板后落盘。
