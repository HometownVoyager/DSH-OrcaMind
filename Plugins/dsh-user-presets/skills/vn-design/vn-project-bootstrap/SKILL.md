# 视觉小说项目搭建（vn-project-bootstrap）

## 何时使用
- 用户提出开始一部新的视觉小说设计项目且尚无项目目录时。
- 用户要求"新建 VN 项目""开新项目"时。
- 每轮对话开始检阅项目状态、每阶段结束时更新进度。
- 接手已有项目但缺少 README.md 时：先按本 skill 模板补建（已有内容照实填入，不确定处标注待确认），再展开工作。

## 开工规范检查（第一步，落盘 规范-视觉小说设计.md）
每个新项目第一步先检查**工作区主目录**的 `规范-视觉小说设计.md` 与既有文档：
1. 存在用户提供的结构/格式规范且完整 → 直接采用，不再询问；此后每轮 Check 与落盘都以它为唯一规范事实源。
2. 没有、不全，或与默认规范冲突 → 停下询问，给三个方向由用户选：
   - ① 选默认集（本预设内置项目结构与文档体系模板，即 00-设定/ 至 04-资产/ 的目录约定与各文档模板）；
   - ② 新放一份（用户自备设计文档规范或团队内部规范，等待用户放入工作区后继续）；
   - ③ 由 agent 当场起草一份（用 web_search 检索、用 web_fetch 打开原文核对，如商业 VN 企划案规范、团队文档模板），草稿经用户逐条确认后定稿。
3. 选定后落盘 `规范-视觉小说设计.md`（Markdown，统一四节骨架）：
   - ① 来源记录（所选规范集名称、出处与定稿日期）
   - ② 结构与目录约定（整体结构、各部分职能、项目目录与命名）
   - ③ 产出格式规范（标题层级、编号体系、分支与 FLAG 标注格式等要素格式）
   - ④ 红线与禁忌（抽象层级边界、禁止正文台词与引擎代码等）
4. 落点规则：`规范-视觉小说设计.md` 落在**工作区主目录**（与 `<作品名>/` 项目目录并列），一部作品一份规范文档并以作品名区分；同工作区多部作品各自一份，不得互相覆盖。

## 标准目录结构
```
<项目名>/
├── README.md                    # 项目概览：核心创意一句话、当前阶段、确认记录（最先创建，每轮先读）
├── 00-设定/
│   ├── anchors.md               # 全局基准事实层：年龄矩阵/称谓网格/空间拓扑/核心资产与体态状态机（随人物/世界观阶段逐步填实，剧情大纲前锁定）
│   ├── brainstorm.md            # 阶段1：核心创意/主题/情绪基调/目标体验/类型融合/卖点
│   ├── characters/              # 阶段2：主要角色档案，每人一个文件
│   │   └── relationships.md     # 人际关系网与关系变化方向
│   ├── world.md                 # 阶段3：规则/历史
│   ├── factions.md              # 阶段3：势力与组织（与小说、剧本预设同粒度）
│   ├── geography.md             # 阶段3：地理与地点
│   ├── timeline.md              # 历史年表
│   └── glossary.md              # 专有名词表
├── 01-规划/
│   ├── outline.md               # 阶段4：剧情大纲（仅抽象层级，禁止场景与台词）
│   └── chapter-structure.md     # 章节结构表：章节功能、节奏定位与分支点预留
├── 02-系统/
│   ├── systems.md               # 阶段5：交互系统/分支/路线/好感度/章节推进规则
│   └── endings.md               # 结局清单与达成条件、优先级
├── 03-修订/
│   └── continuity-log.md        # 连续性核查与冲突裁决记录（见 vn-continuity）
└── 04-资产/
    ├── asset-list.md            # 阶段6：资产清单（规格/数量/优先级）
    └── notes/                   # 分类明细：bg.md 背景 / sprite.md 立绘 / cg.md CG / bgm.md 音乐 / sfx.md 音效 / ui.md UI / script.md 脚本
```

## `00-设定/anchors.md` 全局基准事实层模板
`00-设定/anchors.md` 是**全局基准事实层**：把最易漂移的常量（出生与年龄、称谓口径、常驻空间拓扑与动线、信物与体态状态）集中成单一事实源，随阶段 2/3 逐步填实，在剧情大纲动笔前锁定，交付下游预设时作为连续性核查的第一基准（下游预设缺该文件时按「只增不改」补建）。

## 执行步骤
1. 与用户确认项目名（暂定）、类型与平台目标——这些决定后续篇幅与资产规格基准。
2. 执行开工规范检查并落盘工作区主目录的 `规范-视觉小说设计.md`（见上）。
3. 创建目录骨架与 README，README 最先创建并填写已知信息；**同时生成 `00-设定/anchors.md`（四节模板占位，随人物/世界观阶段逐步填实）**；各阶段文档先不创建或只留占位，按推进逐份补全。
4. 接手已有项目补建 README 时按现有文档照实填写，无法确认的条目标注「待确认」，不凭空补写；缺 anchors.md 时同样补建占位并从已确认文档照实汇总。
5. 建议下一步：从 vn-brainstorm 开始（00-设定/brainstorm.md）。

## 注意事项
- 六阶段顺序为 Brainstorm → 人物设定 → 世界观设定 → 剧情大纲 → 系统设计 → 资产列表；只有用户确认本阶段完成、或明确指示进入下一阶段后才推进，并在 README 记录该确认。
- **anchors.md 的锁定节点**：剧情大纲动笔前必须完成年龄矩阵、称谓网格与空间拓扑的填写并确认（基准事实先行），后续阶段只读不写；变更锚点先请用户裁决。
- 每轮工作以 README.md 为入口：有则先读再干活，无则先建再干活；连续性核查先对 anchors.md 做定向核验。
- 每阶段产出落盘前按 vn-continuity 执行一次全量核查；查出的冲突先请用户裁决，并记入 03-修订/continuity-log.md。
- 用户要求跳转或回溯时照办，但要在 README 与对话中说明跳转对前后阶段可能产生的影响（如先行资产清单会因设定未定而返工）。
- 用户已有自己的目录习惯时尊重用户结构，但至少保证设定、规划、系统、修订与资产五部分可被找到。
