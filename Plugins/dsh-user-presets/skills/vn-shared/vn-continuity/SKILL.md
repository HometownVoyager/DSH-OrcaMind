# vn-continuity · 一致性核查协议

本 skill 只做一件事：在 `vn-gate` 的 **Check** 步，针对**本轮各子条目（1~4 个、章数不定）**逐个做一致性核查。不探测下游、不做全链全量体检，也不是「顺手改文件」的授权。与 persona【指令裁决】冲突时以 persona 为准。

## 1. 第一基准：`00-Bible/anchors.md` 四节锚点矩阵

`00-Bible/anchors.md` 是剧情大纲前锁定的四节基准事实层，效力高于 `brainstorm.md`（已降级为创意意图记录）、高于各阶段中间稿、高于对话记忆。**四节唯一定义以本表与 `vn-bible/vn-bible-anchors/SKILL.md` 为准**（两者一致）；`00-Bible/00-Bible-四份版/` 下四份 `.docx` 的固定名（核心创意与基准事实 / 角色与关系 / 世界观与地理 / 历史·术语·文风）是**收录文档的分组**，不是 `anchors.md` 的四节，不据此另立一套核查维度。核查时逐节过：

| 节 | 锚点矩阵 | 逐节核查项 |
|---|---|---|
| ① 年龄与生理时间轴矩阵（年龄矩阵） | 各角色当前年龄、关键节点年龄、年月日 / 季节 / 昼夜 / 经过天数 | 是否改变 / 否定已锁定年龄与时间线；是否私自补候选方向或未确认创意缺口 |
| ② 空间拓扑与动线模型 | 建筑属性、户型、动线连接、声光穿透法则、房间 / 门窗朝向、视线与声音遮挡 | 是否与已锁定空间规则矛盾；上下楼方式、地点位置是否同源同写；是否越界补写未确认细节 |
| ③ 称谓三层解耦网格（称谓网格） | 系统 Speaker ID、主观叙述层 / 认知称谓、对白呼告层 | 三层称谓是否一致、不混用或前后打架；矩阵是否被改写、压缩或丢失 |
| ④ 核心资产与体态状态机 | 体貌锚点、信物流转状态机（道具从哪来到哪去、当前持有者、所处阶段、状态迁移条件） | 状态迁移先后是否冲突；角色不可变体貌是否偏离锚点；矩阵是否被改写或丢失 |

四节矩阵中的表格（年龄矩阵 / 称谓网格 / 信物流转状态机）是硬锚点：只比对，不压缩、不改写、不「优化」。时间线、专有名词、文风基调等其余设定事实以 `00-Bible/` 下 `timeline.md` / `glossary.md` / `style.md` 等只读文档作次级参照，不另立第五、第六节。

## 2. 核查范围（消除「全链逐项过」与「不得读下游」的冲突）

```
① 先过 00-Bible/anchors.md 四节锚点矩阵（第一基准）
        ↓
② 再核对本轮产物 与 其【直接上游已确认文件】是否一致
```

- **只看直接上游**：例如 `vn-script` 核对 `01-Plan/` 与 `00-Bible/` 中本轮实际引用的已确认条目，`vn-screenplay` 核对 `02-Script/` 对应场次的已确认底本与 `03-Asset/asset-gap.md`。不逐项遍历 6 个编号目录，不探测下游目录是否存在，不为「下游尚未产出」做存在性判断。
- **不读下游**：此处的核查范围与 `vn-gate` §5 一致，不存在「链路逐项过整条链」与「下游不读取」的张力。
- 链路比对只读上游已确认内容，不以本轮产物为准反向「修正」上游。

## 3. 只核查本轮子条目

- 核查对象恒等于 `vn-gate` 本轮 `本轮子条目` 字段所记的子条目范围（1~4 个：1 个 brainstorm 字段 / 1 个角色档案 / 1 份世界观文件 / 1 章大纲 / 1 条结局条件 / 1 章正文 / 1 个分支段 / 1 类资产规格 / 1 条提示词 / 1 个资产文件 / 1 场演出稿 / 1 份规格 / 1 个工程模块）。逐个核查，不因本轮多章而只抽第一个；用户授权超上限时按授权范围核查。
- 不借 Check 步把整个阶段翻一遍；未列入本轮子条目的文件不读、不评、不改。
- 核查结论只描述「一致 / 冲突」，不附带下游设计建议稿、候选方案或占位内容。
- 即使发现非本轮文件「看起来更好」也不改；Check 不是授权写入步。

## 4. 排除项与只读事实源

- `02-Script/Draft/` 不参与核查：不作核查对象也不作依据，不引用为事实源。
- `01-Plan/endings-and-flags.md` 为结局 / 分支唯一事实源，下游只读；核查时只验证本轮产物是否与其一致，不据此新建同义文件。
- `00-Bible/brainstorm.md` 为创意意图记录，不作基准事实；`README.md` 只作状态读取，不作事实源。
- 四份 `.docx` 是 Markdown 的压缩副本，不作核查基准。

## 5. 冲突处理

- 发现与 §1 锚点矩阵、或核查范围内已确认内容的冲突（命名冲突、事实矛盾、状态机被改写、抽象层级越界），停下，用 `ask_user_question` 报告冲突原文位置与两种候选处置，请用户裁决。
- 不自行改写已确认内容：不改上游、不改本轮产物以「抹平」冲突、不两边各改一点、不把冲突记成「待后续统一」。
- 用户裁决后，在 `README.md` B 区「进度记录」追加一行记入「冲突位置 / 裁决结论 / 裁决人 / 轮次」；A 区状态仍保持「待确认」，不因裁决自行置「已确认」。状态置「已确认」的统一判据是用户在确认中明确认可本轮成果后由 AI 代为登记（见 `vn-gate` §4），用户显式授权时按授权处理；B 区既有行不改写。
- 旧版 `03-修订/continuity-log.md` 已废弃，`03-修订/` 不在白名单内，不创建或写入；一切裁决记 `README.md`。

## 6. 核查结果写进 README

- 无冲突时，Check 结论交给 `vn-gate` 的 Write 步：A 区就地更新 5 字段、B 区按本轮子条目数追加对应行数（一行一产物），每行内容含「轮次 / 该子条目 / 核查结论 = 一致 / 状态 = 待确认」。
- 不把核查结论写成单独文件、写成 `continuity-log.md`、写进 `Specifications.md`；一轮多产物时按产物数追加对应行数，不合并成一行、也不额外追加总结行。
- 状态从「待确认」变「已确认」的默认途径是用户在确认中明确认可；有冲突时本轮不写「一致 / 待确认」行，先停下询问，裁决后再追加确认记录行。
- README 状态登记的默认时点见 `vn-gate` §2（下一轮 Read 之前），不存在「提问后不得写文件」的时序矛盾。
