# 交付验收（staging-acceptance）

## 何时使用
- 宣布某一轮工作完成之前。
- 宣布某一稿次（`draft-vN`）定稿之前。
- 用户要求「验收一下」「看看还差什么」时。
- 移交下游引擎转写之前。

## 验收清单
逐项核验，每项都必须给出**判定依据**（读了哪个文件、比对了什么），不允许凭印象打勾。

| # | 检查项 | 判定方法 | 不通过怎么办 |
|---|--------|----------|--------------|
| 1 | 剧情完整 | 上游章-段逐条能指到场次，无遗漏、无凭空新增 | 补齐漏场；删除无来源的场次或补上来源说明 |
| 2 | 每场齐全 | 每场都有背景、BGM、音效、立绘、演出说明；不适用者已写理由 | 补齐缺失小节；确不适用的写「无 + 理由」 |
| 3 | 引用有据 | 稿中每个 ID 都能在 `资产索引.md` 查到 | 查不到的删掉或改走缺口流程 |
| 4 | 无伪造 | 无编造的路径、ID、差分名、BGM 名、CG 编号 | 逐条替换为真实 ID 或标注为缺口 |
| 5 | 缺口留痕 | 缺口／替代／降级／占位／硬缺失已记入标注区与 `资产缺口.md` | 补齐标注并同步缺口表 |
| 6 | 文本资产已登记 | 生成的无演出剧本已落盘且状态为 `generated` | 补落盘、补登记 |
| 7 | 计划已更新 | `制作计划.md` 场次状态与 README 进度、确认记录已同步 | 补齐状态与登记行 |
| 8 | 无引擎语法 | 稿中无引擎命令、路径、配置、参数表 | 删除实现细节，只留演出意图 |
| 9 | 下游可用 | 场次、资产 ID、演出意图、时机信息自足，无需回问 | 补足缺失字段 |
| 10 | 未默默凑合 | 每处妥协都有标注与裁决记录 | 补标注；未裁决的降级重开裁决 |
| 11 | 未被无谓阻塞 | 能推进的场次都已推进；阻塞项有明确裁决请求 | 恢复推进，或补齐阻塞说明 |
| 12 | 疑问已问、确认已整理 | 本轮疑问已提出并确认，确认结论已整理成清晰文本落盘 | 补问、补整理落盘 |

## 下游转写自足性检查
中间稿将交给下游引擎转写，检查它离开本会话后是否仍然可读：

- [ ] 「规范-演出.md」写清了格式与资产引用语法，下游能自行读懂稿子。
- [ ] `资产索引.md` 给出每个 ID 对应的实际文件位置，路径映射有依据。
- [ ] 每场稿的场次号、地点、时间、出场角色、上游对应关系齐全，便于建立时间轴。
- [ ] 演出意图描述具体到可以据此实现，而不是「气氛热烈一些」这类无法执行的话。
- [ ] 所有缺口状态明确：哪些已裁决、哪些待裁决、哪些必须替换。
- [ ] 稿中不包含任何需要「回头问作者」才能补全的信息；确有必须回问的，已在交付说明中列出。

## 交付说明模板

```markdown
# 交付说明 ｜ <作品名> ｜ draft-v<n> ｜ <日期>

## 交付范围
<覆盖 SC-001 - SC-0XX，共 n 场；对应上游 <章节范围>>

## 资产使用
- 使用资产 <n> 件（available <n> ｜ generated <n> ｜ substitute <n> ｜ placeholder <n>）
- 缺口 <n> 件：已裁决 <n> ｜ 待裁决 <n> ｜ 必须替换 <n>

## 未完成与阻塞
| 场次 | 阻塞原因 | 需要谁裁决 | 建议 |
|------|----------|------------|------|

## 已知妥协
| 场次 | 妥协内容 | 理由 | 裁决记录 |
|------|----------|------|----------|

## 下游注意事项
<转写时需要特别留意的地方：待确认项、必须替换的占位、建议的演出优先级>
```

## 注意事项
- 验收结论要诚实：不通过就列不通过，不要为了让结果好看而放宽判定。
- 验收通过但存在待裁决事项时，明确写出「通过但附带 n 项待裁决」，不要把待裁决算作已完成。
- 验收清单是对用户与下游的承诺，每次验收都按同一套标准过，不要因为赶进度而简化。
- 验收发现的系统性问题是流程问题（如格式规范没定清），除了修补产出，还要建议修订 `规范-演出.md`，避免重复发生。
