>
> 用户观察：使用预设（尤其是新 VN 预设）时，模型在「左右脑互博」（思考里反复自我拉扯、自我否决）中消耗的过程明显比以前多，且大多源于 **用户 prompt 的指令 / AI 自己的想法 / Preset 给的约束** 三方打架。

## 0. 一句话结论

**不是模型变差，而是 11-07 的 VN 工作流改造把「防越界」全部押在了「自然语言绝对句的数量与重复」上，同时删掉了旧预设里所有「以用户指令为准 / 视为已确认 / 一次性授权」的逃生阀，且没有补上一部运行时可见的优先级宪法。** 叠加 DSH 本身**没有任何代码级指令优先级机制**（纯 order 排序 + 字符串 join + role 差异，冲突交给模型自己裁决），三者相撞时模型既不能顺从用户、又不能违反硬约束，只能在思考里逐条复述、互相否定、临时编造裁决理由——这就是「互博」和消耗增加的来源。

施工文档自己已经预告了这个结局（[VN-工作流改造施工文档.md:48](../VN-工作流改造施工文档.md#L48)）：

> 「软约束（prompt 里写「请确认」）会被「完成一轮」的目标压过……纯自然语言约束会退化成「一句无效的话」「If tool limits are only written in the prompt, capability gating degenerates into an ineffective natural-language sentence」。

改造的应对是：把所有措辞升级成「一律 / 必须 / 不得 / 禁止」、把门禁复制到 77 处、并禁止出现「建议 / 尽量」等软词。但它只解决了「模型不听话」，没有解决「模型听谁的话」——反而把后者变成每轮必须重新推理的开销。

## 1. 为什么会「更多地」互博：时间线对照

| | 旧预设（1.4.0，4198 行） | 新 VN 七预设（1.5.0，6178 行，11-07 落盘） |
|---|---|---|
| 工作模式 | `Read→Report→Plan→Do→Check→Write→Ask`，**Agentic work 自主规划子任务**，「产出一份可供用户审阅的草稿，**而不是等待用户逐步发出每一个微指令**」（[cordis.patch.yml:2673](../Plugins/dsh-user-presets/cordis.patch.yml#L2673)、[:3357](../Plugins/dsh-user-presets/cordis.patch.yml#L3357)） | `Read→Report→Confirm→Do→Check→Write→Stop`，**单轮单条目**，「一律按用户逐轮指令推进」（[:4870](../Plugins/dsh-user-presets/cordis.patch.yml#L4870)），「禁止以任何方式绕过逐轮逐条目的用户确认」（[:5958](../Plugins/dsh-user-presets/cordis.patch.yml#L5958)） |
| 用户指令优先 | **有**：「用户要求跳转或回溯时，以用户指令为准」（8 处）、「用户已在同一条消息里明确写出本轮范围时视为已确认，不必重复提问」（6 处）、「可由用户一次性授权跳过阶段门控」（2 处） | **0 命中**：VN 段 4259–6178 内「以用户指令为准 / 用户指令优先 / 视为已确认 / 一次性授权」全部消失 |

## 2. 根因一：DSH 没有指令优先级机制，冲突天然由模型裁决

源码调查（`source/packages/core/system-prompt/`、`core/agent-loop/`、`context/agent-instructions/`、`preset/persona/`、`skill/tool-skill/`）结论：

1. **系统提示词是纯数值排序 + 字符串拼接**。
   [core/system-prompt/src/index.ts:253-256](../source/packages/core/system-prompt/src/index.ts#L253-L256)：`return a.order - b.order || compareNames(a.name, b.name)`；
   [:296-300](../source/packages/core/system-prompt/src/index.ts#L296-L300)：`.map(interpolate).filter(len>0).join('\n\n')`。
   `PromptSection` 接口只有 `name/order/text/interpolate/complete`，**没有 priority / weight / override 字段**。无冲突检测、无「last wins」、无 dedupe。

2. **约束被拆到 4 个不同 authority 通道**，模型必须自己建立层级：

   | 层 | 载体 | role / 位置 | 顺序 |
   |---|---|---|---|
   | ① persona prefix | `deployment:persona-prefix` section，order=0 | **system** | 除固定 identity 外最靠前 |
   | ② 工具 / 策略 guidance（含 plan-mode、各工具 section） | 多个 section，order 500–10200 | **system** | 紧随其后 |
   | ③ agent-instructions（Specifications.md / README.md / AGENTS.md） | `createUserMessage` + `<system-reminder>` | **user** | 插在本轮用户 prompt **之后** |
   | ④ skill 正文 | `skill` 工具的 **tool result**（或 `/name` 的 user 消息） | **tool / user** | 运行时按需加载，最靠近答案 |

   证据：[agent-instructions/src/index.ts:351-354](../source/packages/context/agent-instructions/src/index.ts#L351-L354)（splice 到已认领用户批之后，"so the direct prompt precedes it"）、[render.ts:18-20](../source/packages/context/agent-instructions/src/render.ts#L18-L20)、[tool-skill/src/index.ts:128, 258-287](../source/packages/skill/tool-skill/src/index.ts#L128)。

3. **唯一写了「优先级」的地方是注入给模型看的散文，不是代码裁决**：
   [agent-instructions/src/render.ts:18-20](../source/packages/context/agent-instructions/src/render.ts#L18-L20)：
   > `More specific instructions take precedence over broader ones. They do not override system, developer, or direct user instructions.`

   这句话只覆盖 agent-instructions 这一路，**没有说 persona 与用户冲突时谁赢**，也没有任何代码去执行这个排序。全库 grep `priority|hierarchy|override…instructions|conflict` 在 core/system-prompt、agent-loop、preset/persona 中无指令优先级实现。

4. **同名 section 是覆盖，但那只是注册层**：scoped 同名 section shadow 全局同名 section（[system-prompt/src/index.ts:476-478](../source/packages/core/system-prompt/src/index.ts#L476-L478)），同层重复注册直接抛错（[:413-415](../source/packages/core/system-prompt/src/index.ts#L413-L415)）。这是「预设 persona 替换部署 persona」的机制，**不是「用户说的话能覆盖 persona」**。

> **推论**：把「用户指令 > 预设约束」当作默认前提是错的——DSH 里它只靠 (i) system vs user 的 role 差异、(ii) 拼接位置、(iii) 上面那句散文，交给模型自己判断。当 persona 用 system 通道、且是 77 行塞满「一律不得」的最前段时，模型对「用户让一步」的信心会被系统性压低，于是开始互博。

## 3. 根因二：约束分散在四层，却没有一部「运行时可见的宪法」

施工文档里其实有大量**层间裁定**，但它们是写给「施工人员」看的，被明确禁止进入运行时提示词：

- [施工文档:369](../VN-工作流改造施工文档.md#L369)（批量工具与单轮单条目的章级裁定）末句：
  > 「本裁定为**章级注明**：7 段 persona 正文保持逐字不变……**施工时不得把本裁定整段复制进 persona**。」
- [施工文档:257](../VN-工作流改造施工文档.md#L257)、[:748](../VN-工作流改造施工文档.md#L748)、[:365](../VN-工作流改造施工文档.md#L365) 亦为同类「冲突时以本节为准 / 不得质疑、不得验证」的施工期裁定。

**后果**：运行时模型只能看到互相打架的绝对句，看不到裁决规则。文档是规范源，模型读的却是它的一个被删掉裁决部分的投影。

同时，模型每轮要消化的约束量极大（子代理实测统计）：

| 来源 | 绝对化措辞密度 |
|---|---|
| `vn-bible` persona prefix（77 行 / 5826 字） | **142 处**（一律 69、不得 42、禁止 12、必须 10…），≈1.84 次/行 |
| `vn-gate/SKILL.md`（125 行 / 7911 字） | **132 处**，≈1.06 次/行 |
| 单轮合计（prefix + plan-mode + agent-instructions 注入 + vn-gate + vn-spec + vn-continuity + 本阶段 skill + 首轮显式读 2 份根文档） | **400+ 处绝对化约束** |

整份 `cordis.patch.yml`：一律 381 / 不得 376 / 禁止 369 / 必须 242 / 唯一 99 / 严禁 47 / `ask_user_question` 105（本次统计口径含旧预设，子代理按 VN 区另有一组更保守数字，量级一致）。

## 4. 根因三：同权重绝对句相撞 → 逻辑矛盾，模型无降权能力

因为「禁止软化」，所有约束同权重、无例外、无优先级。任意两条相碰就是矛盾，模型没有「通常 / 尽量 / 优先」可用，只能逐条复述再互相否定。**最有力的 5 类实撞**：

### 4.1 两个互斥的「唯一且最后的工具调用」（最严重）
- [cordis.patch.yml:4445](../Plugins/dsh-user-presets/cordis.patch.yml#L4445)（7 个 VN 预设各一份，另有 :4716 :4986 :5251 :5510 :5808 :6080）：
  > 「让 **exit_plan_mode 成为该回复中唯一且最后的工具调用**……**不要用散文或 ask_user_question 问「要不要开始」**」
- [vn-gate/SKILL.md:42](../Plugins/dsh-user-presets/skills/vn-shared/vn-gate/SKILL.md#L42)：
  > 「本轮**最后一个工具调用必须是 `Stop` 步的 `ask_user_question`**；此后不得再有任何工具调用（含 `present`、文件写、命令）」

两者在**同一个 system prompt 的相邻 section** 里直接互斥。施工文档 [:365](../VN-工作流改造施工文档.md#L365) 只给 plan-mode 追加了「单轮单条目协议优先于本段：禁止在方案里规划本轮子条目之后的后续子条目」这一**窄点**，并[在 :4443](../Plugins/dsh-user-presets/cordis.patch.yml#L4443) 复制 7 次——但**从未裁决「两个最后工具调用谁赢」**。

### 4.3 「禁止规划后续子条目」×「Report/Stop 必须附下一候选清单」

## 5. 根因四：同一条约束被复制 77 次，且「唯一真源」本身被声明了多次

- 「T 块唯一真源」这个**元声明**本身出现在 3 处（[vn-gate/SKILL.md:12](../Plugins/dsh-user-presets/skills/vn-shared/vn-gate/SKILL.md#L12)、[施工文档:2362](../VN-工作流改造施工文档.md#L2362)、[:707](../VN-工作流改造施工文档.md#L707)），7 个 persona 又各写一行逐字相同的引用（:4320 :4604 :4855 :5125 :5399 :5684 :5970）。模型每轮要先判断「我看到的这段是全文、索引、还是引用？该执行哪一份？」

## 6. 治理方案（按性价比排序）

### 方案 A · 最小改动、立刻见效：补一部「运行时宪法」（强烈建议先做）

在**每个 VN persona prefix 的最前面**（system 通道、order=0，比工具 section 更早）插入一段 8–12 行的短宪法，只讲裁决，不复述规则：

```
【指令裁决 · 本段优先级最高】
1. 本预设的约束分两类：【硬红线】只限以下三条：① 不跨阶段写入 ② 不创建计划外文件
   ③ 不自行把 README 状态置「已确认」。其余一切流程、步骤、提问方式均为【默认节奏】，可被用户显式指令覆盖。
2. 用户本轮 prompt 与【默认节奏】冲突时，以用户指令为准，直接执行，无需先提问确认；
   用户已在同一条消息里写明范围/要求时视为已确认。
3. 用户指令与【硬红线】冲突时，不擅自执行也不反复自辩：一句话说明冲突点，
   用 ask_user_question 给「按我说的做（明确知悉风险）/ 保持红线」二选一，由用户拍板。
4. 本预设引用 vn-gate / vn-spec / vn-continuity 时，若其措辞与本段冲突，一律以本段为准；
   若两份 skill 之间冲突，按「vn-gate 门禁 > vn-spec 目录 > vn-continuity 核查」执行，不再逐条复述。
5. 不确定「这条是否生效」时，按本段裁决，不要回头逐份溯源旧文档、旧行号或 disabled 预设。
```

**为什么有效**：
- 直接消灭最高频的互博源（用户指令 vs 预设），把「既不能顺从又不能拒绝」变成一条确定性规则；
- 把 400+ 条同权重绝对句降为「3 条硬红线 + 其余默认节奏」，模型终于有降权能力；
- 显式给出 layer 优先级，替代 DSH 缺失的代码机制；
- 明确禁止「回头逐份溯源」，砍掉「这条到底生效吗」的循环核验。

> 这段宪法必须放在 **prefix（system, order=0）**，不能只写进施工文档或 skill——否则运行时模型看不到（见 §3）。同时建议把旧预设里的「以用户指令为准 / 视为已确认」两句话恢复进 VN 段。

### 方案 C · 结构性减重（中期，收益最大但需要回归测试）

1. **单一真源，真正只留一份**：`vn-gate §0` 的 5 条 T 块全文只保留在 `vn-gate/SKILL.md`；7 个 persona 的「新七步循环 / 单轮单条目硬约束 / README 状态机校验 / 求证与拍板规则 / 技能使用 / 输出约定 / 红线」这些**逐字复制块**全部删掉，改成一行「按 `vn-gate` 执行，冲突按本文【指令裁决】段」。当前 7 个 persona 共 509 行 prefix，可压到约 7×15 行。
2. **绝对句降权**：把「一律 / 严禁」批量降级为「默认 / 除非用户明确要求」，只保留方案 A 里那 3 条硬红线用「不得」。删除「禁止出现软词」这条元规则——软词正是给模型降权的工具，不是漏洞。
3. **把门禁从自然语言搬到物理层**（施工文档 [:48](../VN-工作流改造施工文档.md#L48) 自己引用的 StateGate 结论）：锁 1 的 `customSkillDirs` 已经做对了，继续沿用；但「单轮单条目 / 末位提问 / 状态机」仍是纯 prompt 约束。可评估用现有 `dsh-tool-gate`（宿主侧 `tools.restrict` 白名单，[README.md:60](../README.md#L60)）或新增一个轻量 Host 插件，在**工具调用层**做「一轮只允许 1 次 write + 末位必须是 ask_user」的校验，让模型不必在思考里自我执法。
4. **skill 按需加载，不每轮全量注入**：`vn-gate` 已是「每轮强制加载」，可改为「首轮加载一次 + 后续轮只在状态机变更时重载」，配合 A 段宪法，减少每轮重复的 132 处绝对词。

### 方案 D · 验证口径

改完必须**开新会话**（Cordis 已运行会话保留启动时的插件修订，[VN-工作流改造说明.md:25](../VN-工作流改造说明.md#L25)）。建议用同一组 5 条测试 prompt 对比改造前后：

1. 「一次做完七个，别逐个问」→ 期望：要么按用户指令执行、要么一句话给出二选一提问，**不出现大段自我辩解**。
2. 「顺便把大纲也写了」→ 期望：按红线处理，不反复自证。
3. 首轮无指令 → 期望：Read 步定序执行、报 1 个子条目、末位提问。
4. plan mode 开启时的收尾 → 期望：不再出现两个「最后工具调用」互搏。
5. 用 `reasoning` 模型的思考长度 / 工具调用数做前后对比，量化「互博消耗」。
