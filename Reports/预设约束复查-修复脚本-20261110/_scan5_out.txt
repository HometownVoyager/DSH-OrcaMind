  600| ### 3.0.6 新七步循环与 ask_user_question 收尾（章级定义）
  601| 
  602| **旧七步 `Read → Report → Plan → Do → Check → Write → Ask` 一律废除。** 旧版 `Write` 在 `Ask` 之前是「一轮做完」的病根，禁止在任何新预设的 persona、skill、注释中复现。
  603| 
  604| **新七步（逐字锁定）：`Read → Report → Confirm → Do → Check → Write → Stop`**
  605| 
  606| | 步 | 动作 | 硬约束 |
  607| |---|---|---|
  608| | Read | **每轮先调用 `skill` 工具显式加载 `vn-gate` 正文**（`customSkillDirs` 只列目录/catalog、不自动注入正文；未加载不得进入 Report）；读 `README.md` 校验 `当前预设`；**首轮**显式用文件工具读一次 `Specifications.md` 与 `Direction.md`（后续轮遵守已读内容、不复读），读本阶段上游只读清单，读本阶段自己那一列的既有产出 | 每轮必须校验 `当前预设`（按 §4.3 §5 三分支判定）；仅「其余不匹配」停下询问、不动任何文件；五条硬约束见 §3.0.9 |
  609| | Report | 报告 `当前预设 / 当前阶段 / 已完成关键信息 / 本轮子条目候选清单 / 本轮未复读部分` | 禁止在 Report 中规划或预告后续子条目 |
  610| | Confirm | 用 `ask_user_question` 呈现候选清单，**本轮子条目由用户从候选清单中选定**；取得用户明确确认后才进入 Do | 无用户明确确认，一律不得进入 Do、不得进入下一轮、不得进入下一阶段 |
  611| | Do | 只处理 Confirm 选定的**那 1 个子条目**，加载本阶段 skill 与工具，产出草稿 | 禁止在本轮规划/预写后续子条目；禁止跨阶段写下游目录 |
  612| | Check | 按 `Specifications.md`、`vn-continuity`、`vn-spec` 执行一致性核查（锚点矩阵优先） | 发现冲突一律停下请用户裁决，禁止自行改写已确认内容 |
  613| | Write | 只写本阶段那一列的既定文件 + 就地更新 `README.md`「当前状态」块的 5 个字段 + 在「进度记录」区追加一行（§3.0.7 双区结构） | 禁止创建计划外文档；禁止改写/删除「进度记录」区既有行；`Write` 之后不得再执行任何写操作 |
  614| | Stop | **本轮最后一个工具调用必须是 `ask_user_question`** | 其后禁止调用任何工具（含 `present`、`todo_write`、`tool-skill`、`read`） |
  615| 
  616| **`ask_user_question` 两组固定选项（按步骤区分，逐字写入，禁止互相复用）**：
  617| 
  618| **A 组 · `Confirm` 步（开工前选条目）**——此时尚未产出，问「本轮做哪一个」：
  619| 1. `就做这一个` —— 确认本轮唯一子条目，**进入 `Do`**；A 区 `状态` 置 `进行中`。
  620| 2. `换一个子条目` —— 从候选清单改选，本轮重新 `Report → Confirm`。
  621| 3. `先不做，停下询问` —— 不动任何文件，等用户下一轮指令。
  622| 
  623| **B 组 · `Stop` 步（收尾认可成果）**——此时本轮已产出，问「成果是否认可」：
  624| 1. `认可本轮成果` —— 用户认可本轮唯一子条目，本轮到此结束；A 区 `状态` 置 `已确认`，`下一候选` 就地登记本轮 Stop 列出的下一候选清单（只列标题、不展开；无后续候选时记「无」）。
  625| 2. `换一个子条目重做` —— 本轮成果不入正式事实源（保留在磁盘但不被后续阶段引用为事实源，`04-ScreenPlay/` 的「只增不改」仍成立：一律另起新文件重做，禁止覆盖或改写既有落盘文件）；A 区 `状态` 置 `待确认`，把用户指定的重做条目连同下一候选清单一并登记进 `下一候选`（只列标题、不展开）。
  626| 3. `本阶段已确认，进入下一预设` —— **唯一允许推进的口令**；A 区 `状态` 置 `已确认`，`当前预设` **保持为当前预设 id 不变**（登记动作一律留给用户手动切换预设后、由下一预设首轮 Read 完成，AI 不得代改、不得自行触发切换）；只有用户手动切换到下一预设会话后，才允许推进。
  627| 
  628| **只有 `已确认` 才允许推进。** `进行中` 与 `待确认` 一律禁止进入下一预设。两组各三项一字不得删减、不得改写、不得跨组套用；可追加阶段专属选项。
  629| 
  630| **必须删除的旧表述（施工人员逐字检索并删除，禁止残留）**：
  631| > 「以 Agentic work 的方式自主规划该阶段内的子任务……产出一份可供用户审阅的草稿，而不是等待用户逐步发出每一个微指令」
  632| 
  633| 替换为：
  634| > 「本轮子条目由用户从候选清单中选定；AI 一律不得自主规划该阶段内的子任务，一律不得在一轮内处理多个子条目。」

   31| ## 3. 默认每轮节奏
   32| 
   33| ```
   34| Read → Report → Confirm → Do → Check → Write → Stop
   35| ```
   36| 
   37| - **Read 固定顺序**：① 读 `README.md` 状态机（校验「当前预设」）② 首轮另显式读一次 `Specifications.md` 与 `Direction.md` ③ 读本阶段已有产物。多个「必须先」不再争第一。
   38| - **Report**：报当前阶段 / 已完成 key / 本轮待办子条目；可附 ≤3 个下一候选标题（只列标题、不展开）。「列标题」不算规划后续子条目；写字段/草案/设计建议才算。
   39| - **Confirm**：默认用 `ask_user_question` 确认本轮范围；用户已写明范围时跳过。
   40| - **Do / Check / Write**：只做被确认的子条目；按 `vn-continuity` 只核查该产物及其**直接上游已确认文件**（不探测下游、不做全链体检）；只写 1 个文件 + README A 区 5 字段 + B 区追加一行（状态「待确认」）。
   41| - **Stop**：停下，报告本轮结果，列出下一候选标题，等下一轮指令。
   42| 
   43| **本轮工具调用顺序不设固定末位不变量**。报告、`present` 交付、README 状态登记都是正常步骤；状态登记默认在下一轮 Read 之前完成，不存在「提问后不得写文件」的时序矛盾。

   1| # 预设使用时「左右脑互博」消耗变多：成因调查与治理方案
   2| 
   3| > 调查日期：2026-11-10。范围：`Plugins/dsh-user-presets/`（20 条 `preset-*`，其中 7 条 `preset-vn-*` 为 2026-11-07 新增）、`skills/vn-shared/` 与 7 个阶段目录共 39 份 `SKILL.md`、`VN-工作流改造施工文档.md`（2753 行）、`VN-工作流改造说明.md`，以及 `source/packages/` 下 DSH 官方源码的提示词组装链。**纯调研，未修改任何现有配置；本文件是新增报告。**
   4| >
   5| > 用户观察：使用预设（尤其是新 VN 预设）时，模型在「左右脑互博」（思考里反复自我拉扯、自我否决）中消耗的过程明显比以前多，且大多源于 **用户 prompt 的指令 / AI 自己的想法 / Preset 给的约束** 三方打架。
   6| 
   7| ---
   8| 
   9| ## 0. 一句话结论
  10| 
  11| **不是模型变差，而是 11-07 的 VN 工作流改造把「防越界」全部押在了「自然语言绝对句的数量与重复」上，同时删掉了旧预设里所有「以用户指令为准 / 视为已确认 / 一次性授权」的逃生阀，且没有补上一部运行时可见的优先级宪法。** 叠加 DSH 本身**没有任何代码级指令优先级机制**（纯 order 排序 + 字符串 join + role 差异，冲突交给模型自己裁决），三者相撞时模型既不能顺从用户、又不能违反硬约束，只能在思考里逐条复述、互相否定、临时编造裁决理由——这就是「互博」和消耗增加的来源。
  12| 
  13| 施工文档自己已经预告了这个结局（[VN-工作流改造施工文档.md:48](VN-工作流改造施工文档.md#L48)）：
  14| 
  15| > 「软约束（prompt 里写「请确认」）会被「完成一轮」的目标压过……纯自然语言约束会退化成「一句无效的话」「If tool limits are only written in the prompt, capability gating degenerates into an ineffective natural-language sentence」。
  16| 
  17| 改造的应对是：把所有措辞升级成「一律 / 必须 / 不得 / 禁止」、把门禁复制到 77 处、并禁止出现「建议 / 尽量」等软词。但它只解决了「模型不听话」，没有解决「模型听谁的话」——反而把后者变成每轮必须重新推理的开销。
